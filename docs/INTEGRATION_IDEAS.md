## 1. Зачем это нужно

Текущий «Домовой» — MAX-бот и мини-приложение. Пользовательская авторизация через
`WebApp.initData` подходит продукту и **не должна заменяться** отдельными
логинами, паролями или OAuth для жителей и диспетчеров.

Идеи ниже нужны для другого сценария: чтобы в будущем подключать 1С, CRM
управляющей организации, АДС, ГИС ЖКХ или региональную систему отдельным
адаптером, не меняя SLA-движок, жизненный цикл заявки и пользовательские
сценарии MAX.

Целевое обещание:

> Новая внешняя система подключается через адаптер и канонический контракт без
> изменения доменного ядра «Домового».

Фраза «интегрируется с любым сервисом без доработок» некорректна: у систем
разные протоколы, идентификаторы, статусы и справочники. Реалистичная цель —
свести каждое новое подключение к небольшому адаптеру и настройке отображений.

## 2. Что уже есть и можно переиспользовать

- доменные правила заявки и SLA отделены от HTTP, MAX и PostgreSQL;
- use case'ы принимают команды и не зависят от интерфейса мини-приложения;
- есть OpenAPI для `/api/v1`;
- есть inbox для дедупликации событий MAX;
- есть transactional outbox для уведомлений;
- ML и LLM подключаются через порты с fallback — это пример нужного подхода к
  внешним системам;
- URL API уже версионирован.

Этой базы достаточно, чтобы развивать интеграции постепенно, без перестройки
всего приложения.

## 3. Принципы будущих интеграций

1. **MAX остаётся главным пользовательским интерфейсом.** Житель и диспетчер
   входят через MAX, отдельная пользовательская авторизация не нужна.
2. **Домен не знает конкретную CRM.** Термины и статусы внешней системы
   преобразуются в адаптере.
3. **Повтор безопасен.** Повторная доставка запроса или события не создаёт
   вторую заявку и не ломает статус.
4. **Событие сначала сохраняется.** Ответ `200` вебхуку даётся только после
   долговременной записи входящего события.
5. **Синхронизация двусторонняя.** Внешняя система может передать заявку или
   статус и получить изменения «Домового» обратно.
6. **Источник виден.** По каждой заявке понятно, откуда она пришла и с какой
   записью внешней системы связана.
7. **Сбой интеграции не ломает MAX-сценарий.** Непереданное событие остаётся в
   очереди и может быть повторено.
8. **ПДн передаются минимально.** По умолчанию наружу уходят данные заявки и
   технические идентификаторы, а не профиль MAX.

## 4. Интеграционные улучшения — пока не одобрено

Все пункты этого раздела имеют статус **[ИДЕЯ — НЕ ОДОБРЕНО]**.

### I-01. Внешний идентификатор и источник заявки

Добавить к заявке или отдельной таблице связей:

```text
source_system     — max, 1c, crm, ads, gis_gkh, import
external_id       — id заявки во внешней системе
external_url      — ссылка на карточку, если допустимо
last_synced_at    — время последной успешной синхронизации
```

Уникальность: `(company_id, source_system, external_id)`.

Польза: одна заявка имеет номер «Домового» и номер CRM, а повторный импорт не
создаёт дубль.

### I-02. Идемпотентные команды

Для создания заявки и изменения статуса принимать `Idempotency-Key` или
`external_event_id`. Результат первого выполнения сохранять и возвращать при
повторе с тем же ключом.

Проверяемое поведение:

- два одинаковых запроса создают одну заявку;
- повтор статуса возвращает успешный текущий результат;
- повтор с тем же ключом, но другим телом отклоняется как конфликт.

### I-03. Надёжный inbox входящих событий

Расширить inbox:

```text
event_id
source_system
dedup_key
payload
status: pending | processing | processed | failed | dead_letter
attempts
received_at
processed_at
next_attempt_at
last_error
```

Последовательность:

```text
webhook → проверка → INSERT inbox → COMMIT → 200 OK → worker → use case
```

Сейчас особенно важно не отмечать событие обработанным до успешного выполнения
handler/use case.

### I-04. Универсальные доменные события и event outbox

Отделить событие продукта от способа доставки. Минимальный набор:

- `ticket.created`;
- `ticket.status_changed`;
- `ticket.overdue`;
- `ticket.confirmed`;
- `ticket.reopened`;
- `ticket.escalated`.

Предлагаемый envelope:

```json
{
  "event_id": "uuid",
  "event_type": "ticket.status_changed",
  "schema_version": 1,
  "occurred_at": "2026-09-30T09:00:00+03:00",
  "company_id": "uuid",
  "aggregate_id": "ticket-uuid",
  "data": {}
}
```

MAX-уведомления и внешние webhooks должны стать разными подписчиками на одно
событие, а не разными ветками бизнес-логики.

### I-05. Исходящие webhooks

Дать внешней системе возможность подписаться на выбранные типы событий.

Минимальные свойства доставки:

- HMAC-подпись тела;
- уникальный `event_id`;
- timeout;
- retry с backoff;
- журнал попыток;
- dead-letter;
- ручной replay;
- тестовый webhook из интерфейса или CLI.

Полноценный OAuth для этого не обязателен. Для пилота достаточно уникального
секрета конкретной интеграции. Если реального внешнего клиента нет, механизм
авторизации можно отложить и показать на mock-адаптере.

### I-06. Порт внешней системы заявок

Предлагаемый смысл интерфейса:

```python
class ExternalTicketGateway(Protocol):
    async def create_or_update(self, ticket: TicketExport) -> ExternalReference: ...
    async def add_comment(self, ticket: TicketExport, comment: str) -> None: ...
    async def change_status(self, ticket: TicketExport) -> None: ...
```

Конкретные реализации могут быть `OneCAdapter`, `CrmAdapter`, `AdsAdapter`,
`GisGkhAdapter` или `MockCrmAdapter`. Названия приведены как иллюстрация, а не
как утверждённый план.

### I-07. Таблица отображения статусов и категорий

Не зашивать названия конкретной CRM в домен. Для каждого подключения хранить
mapping:

```text
Домовой.registered    ↔ CRM.NEW
Домовой.acknowledged  ↔ CRM.ACCEPTED
Домовой.in_progress   ↔ CRM.WORKING
Домовой.done          ↔ CRM.WAITING_FOR_CLIENT
Домовой.confirmed     ↔ CRM.CLOSED
```

То же требуется для категорий, аварийности, домов и ответственных организаций.
Неизвестное значение должно попадать в карантин, а не молча становиться
`other`.

### I-08. API инкрементальной синхронизации

Для получения изменений добавить:

- cursor pagination;
- `updated_since`;
- фильтры по `company_id`, дому, статусу и источнику;
- стабильную сортировку;
- `next_cursor`;
- возможность повторно забрать изменения после сбоя.

Это важнее большого количества специализированных endpoint'ов: внешний сервис
сможет восстановить состояние даже после временной недоступности webhook.

### I-09. Синхронизация справочников

В перспективе понадобятся операции upsert для:

- управляющих организаций;
- домов и ФИАС/GAR ID;
- диспетчеров;
- соответствий «дом → УО»;
- контактов ГЖИ и РСО;
- региональных настроек и календаря.

Для первого пилота достаточно CSV или JSON-импорта с dry-run, отчётом об
ошибках и безопасным повторным запуском.

### I-10. OpenAPI как внешний контракт

Дополнить схему:

- `securitySchemes`;
- `servers`;
- все ответы `401`, `403`, `404`, `409`, `429`, `5xx`;
- единую схему `ProblemDetails`;
- примеры запросов и ответов;
- webhook/event-схемы;
- правила совместимости и вывода версии из эксплуатации.

Контракт нужно проверять в CI: schema diff не должен пропускать несовместимое
изменение без новой версии.

### I-11. Наблюдаемость интеграций

Для каждой интеграции показывать:

- время последнего успешного входящего и исходящего события;
- размер очереди;
- число retry и dead-letter;
- задержку доставки;
- correlation/request ID;
- последнее сообщение об ошибке без секретов и ПДн.

### I-12. Mock CRM как доказательство расширяемости

Сделать маленький демонстрационный сервис или тестовый адаптер:

1. MAX создаёт заявку;
2. mock CRM получает `ticket.created`;
3. mock CRM возвращает внешний номер;
4. диспетчер меняет статус в CRM;
5. статус появляется в MAX;
6. повтор любого шага не создаёт дубль.

Это сильнее утверждения «можем интегрировать»: проверяющий увидит двусторонний
контур на одной заявке.

### I-13. Двусторонняя интеграция с CRM/АДС через API

> **Статус: [ИДЕЯ — НЕ ОДОБРЕНО, НЕ РЕАЛИЗОВАНО].** Сейчас «Домовой» не
> создаёт заявки в реальной CRM и не получает из неё статусы. Существующий
> `/api/v1` обслуживает мини-приложение MAX и не является готовым внешним CRM
> API.

#### I-13.1. Какую проблему решаем

У большинства УО уже есть АДС, 1С или отдельная CRM. Если заявка из MAX живёт
только в «Домовом», возникают две параллельные очереди:

- диспетчер вручную переносит адрес, текст и срок;
- заявка получает два несвязанных номера;
- статусы расходятся;
- житель видит одно состояние, а УО — другое;
- при повторной отправке появляются дубли;
- внедрение воспринимается как замена рабочей системы УО.

Предлагаемая модель: «Домовой» остаётся MAX-интерфейсом жителя и владельцем
нормативного SLA, а CRM остаётся рабочим местом диспетчера. Между ними работает
двусторонний адаптер.

```text
Житель
   │ сообщение, фото, подтверждение
   ▼
MAX-бот / мини-приложение
   │
   ▼
«Домовой»: заявка, нормативный SLA, история, коллективность
   │                                         ▲
   │ create/update                           │ webhook/status
   ▼                                         │
адаптер конкретной CRM ──────────────────────┘
   │
   ▼
CRM/АДС УО: назначение исполнителя, рабочие комментарии, закрытие
```

Житель никогда не входит в CRM и ничего не отправляет туда самостоятельно.
Все действия жителя происходят в MAX, а обмен выполняет backend «Домового».

#### I-13.2. Основной сквозной сценарий

1. Житель пишет в MAX: «Не работает лифт».
2. «Домовой» классифицирует обращение и рассчитывает нормативный срок.
3. В своей базе «Домовой» создаёт заявку `2026-01042`.
4. В той же транзакции создаётся исходящее событие `ticket.created`.
5. Worker передаёт событие в адаптер CRM.
6. Адаптер преобразует категории и статусы «Домового» в формат CRM.
7. CRM создаёт заявку `АДС-58391` и возвращает внешний идентификатор.
8. «Домовой» сохраняет связь `2026-01042 ↔ АДС-58391`.
9. В карточке MAX появляется внешний номер без ссылки на закрытый интерфейс CRM.
10. Диспетчер принимает заявку в своей CRM и пишет: «Мастер выехал».
11. CRM отправляет webhook в «Домовой».
12. «Домовой» безопасно применяет событие один раз, обновляет свою заявку и
    уведомляет жителя в MAX.
13. CRM ставит «Выполнено».
14. В MAX жителю приходит вопрос «Проблема устранена?».
15. Ответ «Да» переводит заявку в `confirmed` и может закрыть её в CRM.
16. Ответ «Нет» переоткрывает заявку и отправляет событие обратно в CRM.

#### I-13.3. Возможные модели подключения

##### Вариант A. «Домовой» вызывает API CRM — предпочтительный

Подходит, если у CRM есть документированный REST/SOAP API и УО выдаёт доступ.

```text
«Домовой» → POST /tickets CRM
«Домовой» → PATCH /tickets/{id} CRM
CRM → POST /integration/v1/events «Домового»
```

Плюсы:

- заявка попадает в CRM сразу после создания;
- диспетчер не меняет привычный интерфейс;
- retry и контроль доставки находятся у «Домового»;
- адаптер изолирует особенности конкретной CRM.

Минусы:

- для каждой CRM нужен отдельный адаптер;
- нужны доступ, документация и тестовый стенд CRM;
- не все системы поддерживают webhooks.

##### Вариант B. CRM вызывает API «Домового»

Мы публикуем стабильный `/integration/v1`, а разработчик CRM реализует обмен.

```text
CRM → GET /integration/v1/tickets?updated_since=...
CRM → POST /integration/v1/tickets/{id}/status
CRM → POST /integration/v1/events
```

Плюсы: одна спецификация «Домового», меньше кода на нашей стороне.

Минусы: интеграция не появится автоматически — владелец CRM должен реализовать
клиент и поддерживать его.

##### Вариант C. Файловый обмен

Для системы без API использовать CSV/JSON:

1. УО выгружает файл из своей системы;
2. dry-run проверяет адреса, статусы и дубли;
3. оператор исправляет ошибки;
4. импорт применяет изменения;
5. «Домовой» формирует файл обратной выгрузки.

Это не realtime, но может быть самым реалистичным первым подключением для
небольшой УО.

##### Рекомендуемая целевая модель

Гибрид:

- push из «Домового» при создании заявки;
- webhook из CRM при изменении статуса;
- периодическая сверка через `updated_since` на случай потери webhook;
- файловый импорт как fallback для систем без API.

#### I-13.4. Предлагаемый внешний API «Домового»

API мини-приложения `/api/v1` лучше не расширять CRM-операциями. Для машинного
обмена предлагается отдельное пространство `/integration/v1`.

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/integration/v1/tickets` | создать или связать внешнюю заявку |
| GET | `/integration/v1/tickets/{id}` | получить каноническую карточку |
| GET | `/integration/v1/tickets` | инкрементальная выгрузка с cursor/`updated_since` |
| POST | `/integration/v1/tickets/{id}/status` | передать статус CRM |
| POST | `/integration/v1/tickets/{id}/comments` | передать видимый жителю комментарий |
| POST | `/integration/v1/events` | принять универсальное событие CRM |
| POST | `/integration/v1/webhooks` | зарегистрировать исходящий webhook |
| POST | `/integration/v1/webhooks/{id}/test` | проверить доставку и подпись |
| POST | `/integration/v1/reconcile` | запустить сверку расхождений |

Этот список — эскиз контракта, а не утверждённый API.

#### I-13.5. Создание заявки в CRM

Пример запроса адаптера к CRM:

```http
POST /api/tickets HTTP/1.1
Authorization: Bearer <crm-api-key>
Content-Type: application/json
Idempotency-Key: domovoy:ticket:018f...
```

```json
{
  "source_system": "domovoy",
  "external_id": "018f8b75-80d1-7a44-9c16-2f00d6764fb9",
  "number": "2026-01042",
  "building": {
    "external_id": "fias-or-crm-building-id",
    "address": "г. Псков, ул. Примерная, д. 10"
  },
  "category": "lift",
  "is_emergency": false,
  "description": "Лифт не работает",
  "registered_at": "2026-09-30T09:00:00+03:00",
  "react_by": null,
  "resolve_by": "2026-10-01T09:00:00+03:00",
  "deadline_basis": "Правила № 170, приложение 2"
}
```

Пример ответа CRM:

```json
{
  "id": "58391",
  "number": "АДС-58391",
  "status": "NEW",
  "created_at": "2026-09-30T09:00:02+03:00"
}
```

В исходящий payload не нужно включать MAX user ID, токен бота, полную историю
чата и другие данные, не необходимые УО для исполнения заявки.

#### I-13.6. Получение статуса из CRM

Пример webhook CRM:

```http
POST /integration/v1/events HTTP/1.1
X-Integration-Id: comfort-crm
X-Integration-Timestamp: 1790758800
X-Integration-Signature: sha256=<hmac>
Content-Type: application/json
```

```json
{
  "event_id": "comfort-crm:event:9281",
  "event_type": "ticket.status_changed",
  "occurred_at": "2026-09-30T10:00:00+03:00",
  "ticket": {
    "external_id": "58391",
    "domovoy_id": "018f8b75-80d1-7a44-9c16-2f00d6764fb9"
  },
  "data": {
    "status": "WORKING",
    "comment": "Мастер выехал"
  }
}
```

Обработка:

1. проверить integration ID, подпись и допустимое отклонение timestamp;
2. сохранить исходное тело в durable inbox;
3. вернуть `202 Accepted` или `200 OK` после commit;
4. worker находит связь с заявкой;
5. mapping преобразует `WORKING` в `in_progress`;
6. доменный use case проверяет переход;
7. в одной транзакции обновляются заявка и event outbox;
8. житель получает уведомление через существующий MAX-канал.

#### I-13.7. Хранение связи с CRM

Необязательно добавлять CRM-поля прямо в `tickets`. Более гибкий вариант —
отдельная таблица:

```text
external_ticket_links
  id
  ticket_id
  integration_id
  external_id
  external_number
  external_url              nullable
  external_status
  sync_status               pending | synced | conflict | failed
  last_synced_at
  last_external_updated_at
  last_error                nullable

UNIQUE(integration_id, external_id)
UNIQUE(ticket_id, integration_id)
```

Отдельно понадобится конфигурация подключения:

```text
integrations
  id
  company_id
  kind                      mock_crm | one_c | custom_rest | file
  name
  enabled
  encrypted_credentials
  webhook_secret
  settings
  created_at
  updated_at
```

Секреты нельзя хранить внутри `settings` открытым текстом или возвращать через
API.

#### I-13.8. Mapping статусов и правила конфликтов

Пример mapping:

| CRM | «Домовой» | Допустимое действие |
|---|---|---|
| `NEW` | `registered` | заявка зарегистрирована |
| `ACCEPTED` | `acknowledged` | УО подтвердила получение |
| `WORKING` | `in_progress` | назначен исполнитель |
| `DONE` | `done` | запросить подтверждение жителя |
| `CLOSED` | `confirmed` | только после подтверждения жителя |
| `REJECTED` | `rejected` | сохранить причину отказа |

Критичное правило: CRM не должна автоматически переводить `done` в
`confirmed`, если продукт обещает подтверждение результата жителем.

Примеры конфликтов:

- CRM прислала `CLOSED`, но житель выбрал «Не починили»;
- CRM прислала старое событие после более нового;
- неизвестный статус CRM;
- заявка перенесена в другую УО;
- один внешний ID связан с двумя заявками.

Такие случаи должны получать `sync_status=conflict` и попадать в очередь ручной
проверки. Их нельзя молча исправлять последним пришедшим значением.

#### I-13.9. Идемпотентность и порядок событий

Минимальные гарантии:

- `event_id` уникален в пределах интеграции;
- повтор `ticket.created` возвращает уже созданный внешний номер;
- повтор статуса не создаёт второе событие таймлайна;
- событие старше уже применённого не откатывает заявку;
- одинаковый idempotency key с другим телом даёт конфликт;
- исходящие события доставляются как минимум один раз, а получатель обязан
  дедуплицировать их по `event_id`.

Для строгого порядка можно добавить последовательный `aggregate_version`:

```json
{
  "aggregate_id": "ticket-uuid",
  "aggregate_version": 7
}
```

Если пришла версия 9 без версии 8, интеграция запускает сверку карточки, а не
угадывает пропущенное изменение.

#### I-13.10. Ошибки, retry и восстановление

| Ситуация | Поведение |
|---|---|
| CRM недоступна | заявка в «Домовом» создаётся; экспорт остаётся `pending` |
| CRM вернула `429` | повторить после `Retry-After` |
| CRM вернула `5xx` | exponential backoff с лимитом попыток |
| CRM вернула `4xx` из-за данных | не повторять бесконечно; `failed`/карантин |
| timeout после отправки | повторить с тем же idempotency key |
| webhook пришёл повторно | вернуть успех, второй раз не применять |
| webhook не пришёл | периодическая сверка по `updated_since` |
| исчерпаны попытки | dead-letter, уведомление оператору, ручной replay |

MAX-сценарий не должен блокироваться ожиданием CRM. Житель сразу получает номер
«Домового», а состояние интеграции можно показать отдельной нейтральной строкой:
«Передача в систему УО выполняется» или «УО получило заявку № АДС-58391».

#### I-13.11. Авторизация и безопасность

Пользовательская авторизация остаётся только через MAX. Отдельная защита нужна
лишь машинному обмену.

Для пилота достаточно:

- отдельного секрета на каждое подключение;
- HMAC-подписи тела webhook;
- timestamp против replay-атак;
- HTTPS;
- ротации секрета;
- ограничения подключения конкретной УО;
- audit log без токенов и ПДн.

Если появятся несколько реальных партнёров и самостоятельное управление
доступами, можно рассмотреть API keys со scopes или OAuth2 Client Credentials.
Для текущего MVP это не обязательное требование.

#### I-13.12. Как работать с CRM без webhook

Если CRM умеет только отдавать список заявок:

1. worker раз в несколько минут вызывает `GET /tickets?updated_since=...`;
2. сохраняет cursor только после успешной обработки всей страницы;
3. применяет события идемпотентно;
4. периодически делает полную контрольную сверку открытых заявок;
5. не меняет подтверждённую жителем заявку без правила разрешения конфликта.

Если CRM вообще не имеет API, использовать I-09: файловый импорт и экспорт.

#### I-13.13. Mock CRM для демонстрации

Минимальный mock может иметь три экрана/операции:

- список поступивших заявок;
- карточка с внешним номером;
- кнопки «Принять», «В работу», «Выполнено».

Демонстрационный флоу:

1. создать заявку в MAX;
2. открыть mock CRM и показать ту же заявку с номером АДС;
3. нажать «В работу»;
4. показать уведомление в MAX;
5. нажать «Выполнено»;
6. в MAX ответить «Не починили»;
7. показать переоткрытие в mock CRM;
8. повторно отправить одно событие и показать отсутствие дубля;
9. временно выключить mock CRM, создать заявку, включить его и показать retry.

Такой сценарий доказывает двусторонний обмен, идемпотентность и устойчивость,
не создавая ложного впечатления о готовой интеграции с конкретным вендором.

#### I-13.14. Этапы возможной реализации

**Этап 1 — контракт и mock:**

- определить канонический `TicketExport` и event envelope;
- добавить `external_ticket_links`;
- выделить `ExternalTicketGateway`;
- сделать `MockCrmAdapter`;
- покрыть полный флоу тестом.

**Этап 2 — надёжность:**

- durable inbox;
- универсальный event outbox;
- retry, dead-letter и replay;
- idempotency keys;
- конфликтная очередь.

**Этап 3 — внешний API:**

- `/integration/v1`;
- HMAC или API key;
- OpenAPI с примерами и всеми ошибками;
- cursor/`updated_since`;
- contract tests.

**Этап 4 — первый реальный адаптер:**

- получить документацию и тестовый доступ выбранной CRM;
- согласовать mapping и источник истины;
- реализовать адаптер;
- провести пилот на одной УО и нескольких домах;
- измерить долю успешной доставки, задержку и число конфликтов.

#### I-13.15. Критерии готовности

Идею можно считать реализованной для mock CRM, если:

1. заявка из MAX автоматически появляется в CRM;
2. внешний номер виден в «Домовом»;
3. статус CRM отражается в MAX;
4. подтверждение или переоткрытие жителем возвращается в CRM;
5. повтор события не создаёт дубликат;
6. временная недоступность CRM не мешает создать заявку;
7. после восстановления очередь доставляется автоматически;
8. неизвестный статус не портит заявку и попадает в карантин;
9. секреты и MAX user ID не попадают в payload и логи;
10. сценарий покрыт автоматическим integration/contract тестом.

Для заявления о реальной CRM-интеграции дополнительно нужны документация
вендора, тестовый контур, согласие владельца системы и проверка полного флоу на
его стороне.

#### I-13.16. Открытые продуктовые решения

До реализации команда должна выбрать:

- первую целевую CRM или формат mock;
- кто источник истины по каждому статусу;
- показывать ли жителю внешний номер;
- какие комментарии CRM можно показывать жителю;
- передавать ли фото и как долго хранить ссылки;
- что делать с заявкой при смене УО;
- какой срок retry и хранения dead-letter;
- разрешён ли CRM-диспетчеру отказ без подтверждённой причины;
- что делать, если CRM назначила срок позже нормативного;
- является ли интеграция частью продукта или только демонстрацией
  архитектурной готовности.

## 5. Рекомендуемый минимальный пакет — тоже не одобрено

Если команда решит доказывать простоту интеграции, минимальный разумный объём:

1. I-01: `source_system` и `external_id`;
2. I-02: идемпотентность;
3. I-03: надёжный inbox;
4. I-04: универсальный event outbox;
5. I-06: порт `ExternalTicketGateway`;
6. I-12: mock CRM.

Остальное можно показать как дорожную карту. OAuth, Kafka, SOAP и реальную ГИС
ЖКХ ради демонстрации добавлять не требуется.

## 6. Killer-фичи — только идеи, не одобрено

> **Весь раздел имеет статус [ИДЕЯ — НЕ ОДОБРЕНО].** Эти функции не входят в
> текущий P0/P1/P2 и не должны упоминаться как реализованные.

### K-01. SLA API — «нормативный срок как сервис»

Внешняя CRM передаёт категорию, аварийность, регион и время регистрации, а
«Домовой» возвращает:

- срок реакции;
- срок устранения;
- правовое основание;
- предупреждения о неполных данных;
- версию нормативного правила.

Почему может стать killer-фичей: УО сможет сохранить свою CRM, но получить
главное отличие «Домового» — проверяемый нормативный SLA. Это резко снижает
порог внедрения: не нужно заменять существующую диспетчерскую.

Минимальное демо: endpoint `/integration/v1/sla/calculate` и пример вызова из
mock CRM.

### K-02. «Два номера — одна заявка»

Карточка в MAX показывает одновременно номер «Домового» и номер АДС/CRM. Любое
изменение статуса синхронизируется в обе стороны, а расхождение подсвечивается:
«В CRM закрыто, житель не подтвердил».

Почему может стать killer-фичей: устраняет главный страх УО — ещё один кабинет
и двойной ввод, сохраняя независимое подтверждение жителя.

### K-03. Детектор массовой аварии по нескольким домам

Система объединяет похожие обращения из соседних домов в один инцидент РСО:
например, отсутствие воды в квартале. Жители сохраняют собственные заявки, но
диспетчер видит общий корневой инцидент и обновляет их одним действием.

Почему может стать killer-фичей: коллективность выходит за пределы одного
домового чата и помогает отличать проблему дома от аварии на внешней сети.

Риск: без реальных данных и географии легко получить ложные объединения.

### K-04. «Смена УО без потери связи»

После обновления реестра «дом → УО» система:

- показывает оператору diff;
- отключает старую интеграцию УО;
- назначает новую;
- сохраняет историю заявок дома;
- публикует в MAX проверенное уведомление и новые контакты;
- переводит незакрытые заявки по утверждённому правилу.

Почему может стать killer-фичей: закрывает боль эксперта о потере связи при
смене управляющей организации и усиливает региональное масштабирование.

### K-05. Проверяемая цепочка доказательств

Каждое значимое событие получает время, источник, внешний номер и неизменяемый
идентификатор. При просрочке PDF содержит не только таймлайн, но и подтверждения
доставки в УО/CRM и ответы внешней системы.

Почему может стать killer-фичей: превращает переписку в доказательную историю,
полезную жителю, УО и жилищной инспекции.

Важно: не называть такую историю юридически значимой без отдельной правовой
проверки и подходящей электронной подписи.

### K-06. Конструктор адаптера без кода

Администратор загружает пример JSON/CSV, сопоставляет поля и статусы, запускает
dry-run и получает отчёт: что распознано, что потеряется, где конфликт.
Сохранённая конфигурация становится простым адаптером импорта/экспорта.

Почему может стать killer-фичей: у небольших УО часто нет собственной команды
разработки, но есть выгрузка из учётной системы.

Риск: полноценный no-code конструктор слишком велик для MVP. Для проверки идеи
достаточно одного формата CSV и файла mapping YAML.

### K-07. Автопроверка качества интеграции

Перед подключением сервис прогоняет партнёра по тестовым сценариям:

- повтор события;
- неизвестный статус;
- просроченная доставка;
- временный `500`;
- нарушение подписи;
- восстановление после разрыва.

Результат — понятный отчёт «интеграция готова / есть 3 проблемы».

Почему может стать killer-фичей: простота внедрения становится измеримой, а не
маркетинговой формулировкой.

### K-08. Региональный радар SLA

Обезличенная витрина для ГЖИ показывает по УО:

- долю заявок в нормативный срок;
- системные просрочки;
- повторные открытия;
- массовые инциденты;
- качество синхронизации с АДС/CRM.

Почему может стать killer-фичей: даёт путь масштабирования от одного дома к
региону и делает «Домовой» инфраструктурным слоем, а не только ботом.

Риски: доступ к данным, правовые основания, методика сравнения УО и защита от
манипуляций должны быть отдельно согласованы.

## 7. Как выбирать killer-фичи

До одобрения каждой идеи команда должна ответить:

1. Какую подтверждённую боль она закрывает?
2. Кто конкретный пользователь и покупатель?
3. Можно ли показать ценность за 20–30 секунд на демо?
4. Требует ли она реальной внешней интеграции или может быть честно показана на
   синтетике/mock?
5. Не дублирует ли она Госуслуги.Дом или существующую CRM?
6. Какие данные и разрешения нужны?
7. Как измерить результат на пилоте?
8. Что перестанем делать, если берём эту функцию?

Предварительно наиболее сильная связка для обсуждения:

1. **K-01 SLA API** — легко объяснить и связано с уже готовым ядром;
2. **K-02 два номера — одна заявка** — показывает отсутствие двойного ввода;
3. **K-04 смена УО без потери связи** — отвечает на прямую боль эксперта;
4. **K-03 массовая авария** — сильное развитие коллективности, но заметно
   сложнее и рискованнее.

Это не ранжирование команды и не решение о реализации.

## 8. Вопросы, которые требуют решения команды

- Хотим ли мы вообще заявлять публичный интеграционный API или только
  «архитектурную готовность»?
- Какая первая целевая система: 1С, другая CRM УО, АДС или модельная CRM?
- Кто источник истины по статусу: «Домовой» или внешняя система?
- Что происходит, если житель переоткрыл заявку, которую CRM считает закрытой?
- Нужно ли передавать наружу данные жителя или достаточно анонимного actor ID?
- Кто может создавать и менять mappings статусов и категорий?
- Нужна ли синхронизация в реальном времени или достаточно импорта по
  расписанию?
- Как долго хранить payload и ошибки интеграции?
- Какие идеи из раздела 6 переходят в проверяемые гипотезы?

До ответов на эти вопросы документ остаётся только банком идей.

## 9. Что не предлагается добавлять сейчас

- новую пользовательскую авторизацию вместо MAX;
- OAuth2 без реального внешнего клиента;
- Kafka или другой брокер только ради демонстрации архитектуры;
- настоящий обмен с ГИС ЖКХ без официального доступа и контракта;
- универсальный SOAP-конструктор;
- автоматическую юридическую подачу жалобы;
- функции, которые нельзя честно проверить на стенде.
