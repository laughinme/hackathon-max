## Принято

### D-001. Материалы кейса и наши документы разделены (22.09, Claude по ТЗ Марка)
`case/` — только официальные материалы и их саммари, read-only; `docs/` — наши выжимки, гипотезы, решения; `docs/max/` — снимок документации MAX. Почему: критерии требуют отделять факты от гипотез; так проще ссылаться на первоисточник. Альтернативы: всё в одной папке `docs/` — отвергнуто из-за путаницы.

### D-002. Секреты только в `.env`, `.env.example` без значений (22.09, требование кейса)
Почему: критерий «безопасность» (10%), запрет секретов в репозитории (PDF 7). `.gitignore` расширен: `.env*`, `secrets/`, `*.key`, `case/raw/`.

### D-003. Первый прототип бота принят как основа `backend/` (22.09, автор прототипа; переезд по слоям — Claude)
Прототип на `maxapi` 1.2.2 (личный диалог: категория или свободный текст → уточнение → черновик → отправка → «Мои обращения», навигация одним сообщением) смержен в `main` и разложен по слоям из [ARCHITECTURE.md](ARCHITECTURE.md) без изменения логики. Почему: работает, проверен оффлайн-симулятором, код чистый. Что заменяется (см. [PROTOTYPE_REVIEW.md](PROTOTYPE_REVIEW.md)): long polling → вебхук; in-memory → Postgres; модельная «система УК» и демо-таймер статусов → роль диспетчера УО в мини-приложении; UI-поля в домене → рендер в `bot/`.

### D-004. Продуктовая концепция прототипа «chat-first AI-помощник» переработана (22.09, Claude, ждёт подтверждения команды)
Прототип исходил из идеи «житель описывает проблему словами, AI задаёт вопросы и пишет текст обращения». Оставляем личный диалог как точку входа (арендатор, QR, проверяющий), но ядром продукта делаем заявку с нормативным сроком, коллективность в домовом чате и диспетчерскую УО ([PRODUCT.md](PRODUCT.md)). Почему: организаторы предупреждают не начинать с «AI-ассистента»; критерии дают 35 % за масштабирование и ничего за собственную модель; текст обращения жителю не нужен, если заявка сама регистрируется. Альтернатива: оставить концепцию прототипа — проще, но не отличается от десятков команд.

### D-005. ML-классификация жалоб: категория и аварийность через CatBoost, LLM для фото и уточнений; `ml/` (LoRA) удалён (22.09, ML-инженер команды)
**Решение:** два сценария конвейера классификации жалобы.
1. Текст жалобы → классификатор **CatBoost** определяет (а) категорию/подкатегорию (замена `guess_category()` по ключевым словам в [`catalog.py`](../backend/src/domain/tickets/catalog.py)) и (б) **аварийность** (`is_emergency`) — оба выхода идут напрямую в `SlaPolicy(category, is_emergency, ...)` и определяют легальный срок ([DATA.md §2](DATA.md)). Это не сортировка очереди «для удобства» — это тот же механизм, что в справочнике даёт лифту «≤1 сутки» или «≤30 мин», если внутри текста есть признак аварии (топит, искрит, заблокирован человек), а не просто «неисправность». Категория без аварийности не даёт правильный срок и наоборот — нужны оба выхода. Дальше очередь диспетчера сортируется по остатку времени до `resolve_by` (`sort=sla` в [CONTRACTS.md](CONTRACTS.md)) — это уже бесплатно после корректной классификации, отдельная модель «приоритета для сортировки» не нужна. Если к жалобе приложено фото, хостинговая **LLM через API** (провайдер по Q-09) по фото и тексту генерирует более подробное описание, которое прикрепляется к заявке для диспетчера — исходный текст жителя не заменяется.
2. Если уверенность классификатора (по категории или по аварийности) ниже порога, вместо мгновенной регистрации подключается **LLM-чат**: задаёт уточняющие вопросы и/или просит фото (если не приложено), по итогам формирует финальный текст — им заменяется исходное сообщение жителя. Это редкий fallback-путь, не основной сценарий (см. «Почему»). Правило fail-safe: при низкой уверенности именно в аварийности заявка по умолчанию считается аварийной (быстрый срок), пока fallback-диалог не уточнит обратное — недооценённая авария опаснее, чем лишняя быстрая реакция.

Прежний каркас дообучения LoRA в `ml/` (датасет, обучение, оценка, `TRAINING_PLAN.md`) удалён целиком — не потребуется.

**Почему:** CatBoost не требует GPU и обучается за минуты на CPU-датасете — реалистично для 8 дней, в отличие от прежнего плана дообучения LoRA. Аварийность — не отдельная «модель приоритета для сортировки», а обязательный вход SLA-расчёта (правка после обсуждения с ML-инженером: справочник в DATA.md §2 явно показывает, что один и тот же тип проблемы даёт разный срок в зависимости от признаков аварии в тексте, не только от категории/кнопки). Хостинговая LLM только для двух точечных случаев (фото, низкая уверенность) — то, что уже разрешено организаторами и рекомендовано в Q-09, без риска держать свой inference-эндпоинт две недели проверки. Fallback-чат — именно fallback, а не входная точка сценария, поэтому не противоречит предупреждению организаторов не начинать с «AI-ассистента» (D-004).

**Альтернативы:** (а) дообучение LoRA — отклонено, см. [PROTOTYPE_REVIEW §4](PROTOTYPE_REVIEW.md#4-ml-часть-дообучение-lora) (GPU, датасет на 4000 примеров, критерии не награждают свою модель); (б) классификация только кнопками/словарём (исходный P0 из Q-09) — отклонено, не различает аварию и обычную заявку внутри одной категории, только CatBoost на тексте это тянет; (в) отдельная модель приоритета поверх готовой SLA-сортировки — отклонено как избыточное: очередь и так сортируется по времени до дедлайна, как только `is_emergency` определена верно; (г) LLM-классификатор вместо CatBoost — отклонено, дороже по латентности и стоимости на каждую заявку там, где хватает лёгкой модели.

**Открыто (см. также Q-09):** размеченный корпус текстов жалоб для обучения CatBoost, с разметкой не только категории, но и аварийности по формулировке — в [DATA.md §4](DATA.md) есть только распределение по категориям, датасет предстоит собрать/сгенерировать; выбор конкретного vision-провайдера (поддержка изображений у GigaChat/YandexGPT не проверена); порог уверенности для fallback-чата, отдельно для категории и для аварийности.

### D-006. Классификатор — отдельный HTTP-сервис `ml/`, не код в процессе бота (22.09, ML-инженер команды)
**Решение:** CatBoost из D-005 живёт не внутри `backend/`, а отдельным сервисом `ml/` (свой `pyproject.toml`, свой Docker-контейнер, свой процесс FastAPI/uvicorn на порту 8100). Контракт — `POST /classify {text} -> {category_code, category_confidence, is_emergency, emergency_confidence}`, плюс `GET /health`/`GET /ready` (подробно — [CONTRACTS.md](CONTRACTS.md)). Бэкенд обращается туда через `infrastructure/ml/http_classifier.py` (реализация порта `classifier.py` из D-005) и сам откатывается на `RuleBasedClassifier` (ключевые слова), если сервис недоступен, ответил не 200 или вернул 503 (модели ещё не загружены) — тот же паттерн отказоустойчивости, что уже используется для LLM (`infrastructure/llm/service.py` → `StubAIService`). Обученные модели (`.cbm`-файлы, ~10 МБ на обе, плюс `metrics.json`) лежат в репозитории в `ml/models/` (том в `compose.yaml`) — после клона и `docker compose up` классификатор работает сразу, без обучения на сервере; решение ML-инженера от 24.09, вместо первоначального «бинарники не коммитим». Новые модели подхватываются без пересборки образа: перезапустить только сервис `ml`, бот трогать не нужно.

**Почему:** ML-инженер и его датасет-напарник могут разрабатывать, обучать и перезапускать классификатор независимо от Python-окружения бота — не тащить `catboost`/`pandas`/`numpy` (и то, что дальше появится для экспериментов) в тот же venv/образ, что MAX-бот, не ждать друг друга по ревью и деплою. Порт `Classifier` (D-005) для этого и существовал — переключение с in-process адаптера на HTTP не потребовало менять use case'ы или домен, только один адаптер и конфиг.

**Альтернативы:** (а) CatBoost в процессе бота (`infrastructure/ml/catboost_classifier.py`, был реализован и удалён этим решением) — самый простой вариант, CatBoost лёгкий и не требует GPU/vLLM (в отличие от LoRA), но привязывает разработку модели к Python-окружению и релизному циклу бэкенда; отклонено по явному запросу ML-инженера. (б) Не заводить отдельный сервис, обучать модель и коммитить только `.cbm`-файл в `backend/` — не даёт независимости в разработке, тот же venv. Обе альтернативы дешевле по инфраструктуре (на один контейнер меньше) — см. риск ниже.

**Компромисс, который стоит держать в голове:** четвёртый контейнер на двухнедельный период проверки (30.09–14.10) — ещё одна точка отказа сверх уже учтённых в [STATUS.md](STATUS.md) рисков хостинга. Смягчено тем, что откат на правила уже встроен: падение `ml/` не роняет бота, только откатывает классификацию на ключевые слова до перезапуска. `docker compose` и `restart: unless-stopped` для сервиса `ml` — обязательны, как и для `bot`.

### D-007. LLM: хостинговая модель по API с системным промптом и JSON-схемой; без дообучения и без self-host (23.09, Claude по запросу Марка; закрывает спор в команде и Q-09)
**Что говорят организаторы (факты):**
- Обязательных требований к LLM нет: ни «использовать», ни «дообучать». Кейс: чат-бот, мини-приложение, LLM — инструменты, которые «должны помогать решить проблему, а не становиться самоцелью» (PDF стр. 8, рекомендация 4).
- Если LLM работает с нормативкой: привязывать ответы к источникам, показывать основание, предусмотреть случай, когда надёжного ответа нет, не выдавать предположение модели за факт (PDF стр. 18, п. 5).
- Внешние LLM можно, «используйте официальный, документированный API, не храните ключи в репозитории»; при внедрении «в российском контуре» у заказчика могут быть требования к данным и сервисам, зарубежные сервисы «пока не ограничиваем» (Q&A 17.09, запись [00:48:00]–[00:48:49], вопрос про GigaChat API).
- Для разработки и демо — обезличенные данные, «особенно при работе с внешними API и LLM» (Q&A §2, критерий «Безопасность»).
- Бот должен работать 30.09–14.10 без перерывов, «лимиты внешних сервисов не должны закончиться» (Q&A §1). За собственную модель баллов нет, за сложность ради сложности снижают (Q&A §2).

**Решение:** LLM — хостинговая, по официальному API российского провайдера; поведение задаётся системным промптом и строгой JSON-схемой ответа с валидацией и откатом на правила (уже есть: `infrastructure/llm/`, `StubAIService`). Дообучение (LoRA и т. п.) и self-host модели не делаем. Основной провайдер — **Yandex AI Studio**: OpenAI-совместимый endpoint `https://ai.api.cloud.yandex.net/v1`, ключ сервисного аккаунта не истекает, не нужен сертификат Минцифры, текст — YandexGPT, фото — vision-модель из галереи AI Studio (Qwen-VL). Резерв — **GigaChat API** (365 млн токенов в год бесплатно, но OAuth-токен живёт 30 минут, нужен сертификат Минцифры, фото только на платных Pro/Max). Где применяется — только два случая из D-005: описание проблемы по фото и уточняющий диалог при низкой уверенности классификатора; оба P1. Бот полностью работает при `LLM_ENABLED=false`.

**Почему:** требованиям организаторов соответствует любой вариант, поэтому выбираем самый дешёвый по риску. Self-host на 2 недели проверки — GPU, аптайм и деньги без баллов. Дообучение — датасет и время одного человека на все 8 дней (см. [PROTOTYPE_REVIEW §4](PROTOTYPE_REVIEW.md#4-ml-часть-дообучение-lora)). Промпт + JSON-схема + валидация дают управляемость, которую эксперты и проверяют («не выдавать предположение за факт»).

**Альтернативы:** (а) self-host open-weight модели (vLLM) — отклонено: GPU-хостинг на весь период проверки, ещё одна точка отказа; (б) LoRA-дообучение — отклонено ранее (D-005); (в) GigaChat основным — возможен, если команде важнее бесплатная квота, чем простота эксплуатации; (г) зарубежные API — сейчас разрешены, но минус для истории внедрения «в российском контуре».

**Правила использования:** в модель уходят только текст жалобы и фото, без имени, телефона и номера квартиры; в боте просить не фотографировать людей и номера машин; нормативные сроки и основания считает домен (`domain/tickets/sla.py`), а не модель; ключ только в `.env`. Проверить на реальном ключе: работает ли `response_format` с JSON-схемой вместе с картинкой в одном запросе у Yandex (не подтверждено), лимиты размера фото.

### D-008. Ядро заявки: домен, Postgres, один процесс с вебхуком или polling (23.09, Claude, шаг 1 дорожной карты)
**Решение:**
- Агрегат `Ticket` со статусами `registered → acknowledged → in_progress → done → confirmed`, `rejected`; переходы и роли — одна таблица в `domain/tickets/state_machine.py` (диспетчер двигает работу, житель подтверждает или переоткрывает только свою заявку).
- Нормативные сроки — чистая `SlaPolicy`: правило выбирается по категории и аварийности, каждое правило хранит основание; таблица правил — код (`domain/tickets/sla.py`), а не YAML: типизирована и покрыта тестами. Значения помечены «проверить по первоисточнику» до сверки.
- Fail-safe из D-005 реализован без LLM: если уверенность классификатора в аварийности ниже порога, заявка считается аварийной, а бот задаёт один вопрос кнопками «Да, авария / Нет». Ответ жителя определяет срок.
- Postgres через SQLAlchemy 2 async + Alembic; ORM-строки не выходят за `infrastructure/db`, мапперы явные; события заявки — append-only таблица; номер заявки — последовательность БД (`2026-00042`). In-memory адаптер тех же портов — для симулятора и unit-тестов.
- Один процесс FastAPI: `/health`, `/ready`, `POST /webhooks/max` (режим `webhook`, секрет обязателен, переподписка при каждом старте) или фоновая задача polling (режим `polling`, локальная разработка). Зависимости попадают в хендлеры через middleware диспетчера, глобальный `get_services()` удалён.
- Модельная «система УК» (`UKClient`) и демо-таймер статусов удалены: статусы меняет диспетчер через use case `ChangeTicketStatus`.

**Почему:** это общий фундамент для групповых чатов, диспетчерской и эскалации; соответствует требованиям MAX (только вебхуки в проде) и кейса (Docker одной командой, данные не теряются при перезапуске).

**Альтернативы:** отдельные процессы для API и бота — лишний контейнер для MVP; inbox/outbox-очереди на этом шаге — отложены до уведомлений (шаг 2), пока бот отвечает синхронно в пределах 30 секунд.

### D-009. Хостинг: тест на fly.io сейчас, прод — Yandex Cloud VM (23.09, Марк; рекомендация Claude по ресерчу)
**Решение:** для проверки вебхука бэкенд временно развёрнут на fly.io (`https://domovoy-test.fly.dev`, приложения `domovoy-test` и `domovoy-test-db`, регион ams, конфиги в `infra/fly/`). Для сдачи всё переезжает на ВМ в Yandex Cloud (промокод команды): `docker compose --profile prod up -d` — Caddy с Let's Encrypt, бэкенд, Postgres, ML-сервис и статика мини-приложения на одном домене.
**Почему не fly.io / Vercel для сдачи (ресерч 23.09):** зарубежный хостинг вне реестра хостинг-провайдеров РКН; с июня 2025 ТСПУ замедляет зарубежную инфраструктуру (Cloudflare, Hetzner, OVH); IP кастомных доменов Vercel многократно попадали в блокировки в 2026 — проверяющие открывают бота и мини-приложение из России. С 01.07.2025 первичное хранение ПДн граждан РФ обязано быть в РФ (ст. 18 ч. 5 152-ФЗ): user_id и тексты жалоб в базе на fly — формальное нарушение даже для хакатона. Подтверждённых блокировок именно fly.io не найдено; даже российские облака кратко страдали от ТСПУ в июне 2026, поэтому нужен внешний uptime-монитор.
**Оценка стоимости:** ВМ 2 vCPU (50%) / 2–4 ГБ — ~1700–2500 ₽/мес (оценка по открытым прайсам, сверить в калькуляторе); Postgres в Docker на той же ВМ вместо Managed PostgreSQL.
**Важно для команды:** токен бота один. Пока на fly активна подписка на вебхук, `BOT_MODE=polling` на ноутбуке событий не получает (бот пишет об этом в лог и чужой вебхук не трогает; перехватить можно `POLLING_TAKEOVER=true`). Остановить тестовый деплой: `fly scale count 0 -a domovoy-test` и удалить подписку (`DELETE /subscriptions?url=...`).

### D-010. Шаг 2: дома и роли, REST мини-приложения, уведомления через outbox, состояние диалога в Postgres (23.09, Claude)
- Дом, УО, житель (один дом на пользователя в MVP), диспетчер УО; заявка хранит `building_id` и `company_id`. Привязка к дому — по коду из QR-диплинка `?start=h_<код>` или выбором демо-дома.
- Права: двигать работу может только диспетчер УО, которой принадлежит дом; видеть заявку — автор и диспетчеры этой УО (чужим — 404, не 403, чтобы не раскрывать существование).
- Уведомление жителю пишется в таблицу `outbox` в той же транзакции, что и смена статуса; фоновый relay доставляет с ретраями (10 с, 1, 5, 30 мин, затем отказ) и арендой 2 минуты на случай падения процесса. Лимит 2 сообщения/с на получателя. Уведомление «выполнено» содержит кнопки «Да, всё работает / Нет, не починили» — это закрывает цикл без мини-приложения.
- Диспетчер доступен и в чате (очередь, карточка, смена статуса с комментарием) — запасной путь, если организаторы не успеют привязать мини-приложение. Для проверяющих — кнопка «Демо: войти как диспетчер УО» (`DEMO_MODE`).
- REST `/api/v1` для мини-приложения с авторизацией `Authorization: tma <initData>` (HMAC по токену бота, окно 1 час); `dev <id>` — только при `DEV_AUTH_ENABLED=true`. Ошибки — RFC 7807 с `error_code`.
- Чтение отделено от записи: списки и карточки — `TicketQueries` (SQL с JOIN на дома), запись — репозитории и Unit of Work.
- Состояние диалога maxapi хранится в Postgres (`PostgresDialogContext`): черновик переживает перезапуск.
- Вебхук — собственный маршрут: проверка секрета и ответ 200 сразу, разбор и обработка события в фоне. Причина: `maxapi` при разборе синхронно запрашивает чат у MAX API, и любая его ошибка превращалась в 500 (подтверждено на fly 23.09); MAX после 8 часов без 200 снимает подписку.
- Демо-данные: 1 УО, 50 домов в Пскове, 120 исторических заявок; синтетические жители с отрицательными id, им ничего не отправляется.

### D-011. Мини-приложение: отдаёт бэкенд с того же домена, навигация стеком экранов (23.09, Claude)
**Решение:** собранный фронтенд (`frontend/dist`) отдаёт сам бэкенд по `/`, рядом с `/api` и `/webhooks/max`; образ собирается из корня репозитория, этап на Node собирает мини-приложение. URL для формы организаторов — корень домена. Вместо URL-роутера — стек экранов, привязанный к кнопке «Назад» MAX; диплинк `?startapp=t_<id>` открывает заявку. Создание заявки остаётся в боте (чат-первый сценарий), мини-приложение — просмотр, сроки, действия диспетчера и подтверждение жителем.
**Почему:** один домен и один сертификат для вебхука, API и мини-приложения, без CORS; одна точка отказа вместо двух на период проверки; адресной строки в мини-приложении нет, а стек напрямую ложится на `BackButton`.
**Альтернативы:** отдельный хостинг статики (Vercel — риски блокировок и 152-ФЗ, D-009; Object Storage — второй домен и CORS); React Router — лишняя зависимость для трёх экранов. ARCHITECTURE §4 предполагал react-hook-form и zod — формы из одного поля, не понадобились.

### D-012. Шаг 5: просрочки и жалоба в жилинспекцию (23.09, Claude)
**Решение:** фоновая проверка раз в минуту (`DetectOverdueTickets`) находит открытые заявки после `resolve_by`, один раз ставит отметку `overdue_notified_at` и в той же транзакции пишет в outbox уведомления автору («срок истёк, можно пожаловаться») и всем диспетчерам УО. Автор просроченной заявки нажимает «Жалоба в жилинспекцию» (бот или мини-приложение, `POST /tickets/{id}/escalation`) → `Ticket.escalate()` проверяет правило (только автор, только открытая после срока, повтор разрешён, первая дата сохраняется) → бот присылает PDF. Документ собирается в момент отправки из текущей истории заявки (fpdf2, шрифт DejaVu в репозитории). Жалобу подаёт сам житель: мы не отправляем её в реальную инспекцию и не собираем ФИО и адрес — в PDF для них пустые поля.
**Почему:** это главное отличие от «бота заявок»: у нормативного срока появляются последствия. Отметка на агрегате и outbox в одной транзакции исключают двойные уведомления; `SKIP LOCKED` — двойную обработку при двух экземплярах. Миграция 0003 и сид помечают уже просроченные заявки как известные, чтобы первый запуск не завалил диспетчеров старыми уведомлениями.
**Альтернативы:** отдельная таблица эскалаций — избыточно при одной жалобе на заявку; отправка в ГЖИ по API — у инспекций нет единого API, а подача от имени жителя требует его ПДн и подписи; генерация PDF через HTML (WeasyPrint) — тяжёлые системные зависимости в образе.
**Демо-перемотка (24.09):** в `DEMO_MODE` у автора открытой непросроченной заявки есть кнопка «⏩ Демо: срок истёк» (бот и мини-приложение, `POST /tickets/{id}/demo/expire-deadline`). Она сдвигает срок на минуту в прошлое, пишет в историю системное событие «Демо-режим: срок перенесён…» (видно в карточке и в PDF) и в той же транзакции ставит уведомления о просрочке — они приходят через 2–3 секунды (цикл доставки outbox), а не на следующем тике проверки. Частоту проверки (60 с) не трогали: реальным срокам в часы и дни она не нужна, а демо не должно зависеть от неё. Работает только для заявок демо-УО и только автору. Попутно: флаги «подтвердить», «пожаловаться», «демо-срок» считаются от того, автор ли зритель, а не от роли — иначе проверяющий, включивший демо-диспетчера, терял кнопки жителя в своей заявке.
**Проверить до сдачи (Q-13):** формулировки ссылок в жалобе — ч. 2.3 ст. 161 и ст. 20 ЖК РФ, ПП РФ № 416, ст. 12 59-ФЗ — сверить с первоисточниками вместе с таблицей сроков.

### D-013. Шаг 3: домовой чат, «Я тоже», карточка заявки; защита от повторов; /privacy (24.09, Claude)
**Решение.** Бота добавляют в группу → он просит выбрать дом (сменить привязку потом может только тот, кто добавил). В привязанном чате бот реагирует на сообщение, только если классификатор уверен **и** в тексте есть признак жалобы («не работает», «течёт», «опять»…, `domain/chats/complaint_signals.py`) — иначе «кто потерял ключи?» превращалось бы в заявку. Ответ — подсказка со сроком и кнопкой «Оформить» (при сомнении в аварийности — «Да, авария / Нет, обычная»). Нажавший становится автором и жителем этого дома, автор исходного сообщения засчитывается как «Я тоже»; два нажатия дают одну заявку (подсказка блокируется в транзакции). Если в доме уже есть открытая заявка той же категории за 3 дня — бот предлагает «👍 Я тоже», а не дубль. Карточка заявки живёт в чате (срок, статус, число соседей, «Я тоже», «Следить в личке» → `?start=t_<id>`) и перерисовывается через outbox при смене статуса, просрочке и жалобе. Диспетчер видит, скольких соседей касается заявка. Личные и групповые обработчики разведены фильтрами роутеров (`bot/scopes.py`).
**Почему.** Это центральная механика кейса: проблема звучит в домовом чате, а не в личке. «Я тоже» вместо дублей даёт УО один объект работы с весом и показывает масштаб проблемы; публичная карточка со сроком — давление без конфликтов. Фильтр «признак жалобы» ошибается в сторону молчания: незамеченного соседа выручит личка, а надоедливого бота удалят из чата.
**Попутно.** Таблица `inbox`: каждое событие вебхука регистрируется по `mid`/`callback_id`, повторная доставка MAX отбрасывается; ключи старше 3 дней чистятся. `/privacy` и «🔒 Мои данные»: что храним и зачем, удаление (снять дом и роли, стереть черновик, отвязать заявки — они остаются у УО как обращения по дому). Правила-классификатор при ничьей выбирает категорию, названную раньше («лифт … в подъезде» — лифт).
**Ограничения.** Бот замечает сообщения, только если он администратор с правом «Читать все сообщения»; без этого работают `/start` в группе и кнопки. Проверено симулятором и тестами, в реальной группе MAX — проверить руками.

### D-014. Инструменты дома: пульс, листовка с QR, навигатор ответственности (24.09, Claude)
**Решение.** «📊 Пульс дома» за 30 дней: заявки, открытые, просроченные, доля устранённых в нормативный срок, среднее время, частые проблемы, «Я тоже» — в чате и в меню жителя. «🖨 Листовка с QR» (A4 PDF, `segno` + fpdf2): QR ведёт в бота с привязкой к дому, для соседей без чата и арендаторов. «🧭 Кто за что отвечает»: УО, собственник, РСО, регоператор капремонта, регоператор ТКО, муниципалитет, ГЖИ — с основаниями.
**Почему.** Отрыв от «ботов заявок»: прозрачность работы УО на цифрах, путь в сервис для тех, кого нет в чате, и ответ на частый вопрос «а это вообще к кому?». Все цифры пульса — только по заявкам через сервис, это сказано в тексте.

### Q-18. Расширить LLM: классификация свободного текста LLM вместо (или вместе с) CatBoost?
**Рекомендация Claude (решают ML-инженер и команда, затрагивает D-005):** решить по цифрам. Собрать проверочный набор из 150–200 жалоб, **написанных людьми**, не генератором (команда, знакомые, формулировки из реальных домовых чатов без ПДн), разметить категорию и аварийность, сравнить правила, CatBoost и LLM (YandexGPT с JSON-схемой) по точности категории и **полноте по авариям** (пропущенная авария хуже ложной). Порт `Classifier` уже есть, `LlmClassifier` — один адаптер.
Почему сомневаюсь в CatBoost: реальных размеченных данных нет, модель выучит шаблоны генератора, а проверяющие будут писать своими словами; уверенность такой модели плохо откалибрована, и маршрутизация по порогу (D-005) станет ненадёжной. LLM без обучения лучше переносится на незнакомые формулировки, а по цене незаметна: ~0,1–0,2 ₽ за классификацию на YandexGPT Lite (оценка), промокода 5000 ₽ хватит на десятки тысяч вызовов.
Где ещё LLM полезна жителю (по убыванию пользы): извлечь из свободного текста подъезд, этаж, «с какого времени», чтобы бот спрашивал только недостающее; понять в групповом чате, что новое сообщение — про уже открытую заявку («Я тоже», шаг 3); описание по фото (уже в D-005); текст обращения в ГЖИ по фактам из таймлайна. Где LLM нельзя: сроки, ответственность и нормы — только домен с источником.
Результат сравнения — готовый слайд «почему такая механика» для критерия «обоснованность».
