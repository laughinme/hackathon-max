## Принято

### D-001. Материалы кейса и наши документы разделены (22.09, Claude по ТЗ Марка)
`case/` — только официальные материалы и их саммари, read-only; `docs/` — наши выжимки, гипотезы, решения; `docs/max/` — снимок документации MAX. Почему: критерии требуют отделять факты от гипотез; так проще ссылаться на первоисточник. Альтернативы: всё в одной папке `docs/` — отвергнуто из-за путаницы.

### D-002. Секреты только в `.env`, `.env.example` без значений (22.09, требование кейса)
Почему: критерий «безопасность» (10%), запрет секретов в репозитории (PDF 7). `.gitignore` расширен: `.env*`, `secrets/`, `*.key`, `case/raw/`.

### D-003. Первый прототип бота принят как основа `backend/` (22.09, автор прототипа; переезд по слоям — Claude)
Прототип на `maxapi` 1.2.2 (личный диалог: категория или свободный текст → уточнение → черновик → отправка → «Мои обращения», навигация одним сообщением) смержен в `main` и разложен по слоям из [ARCHITECTURE.md](ARCHITECTURE.md) без изменения логики. Почему: работает, проверен оффлайн-симулятором, код чистый. Что заменяется (см. [PROTOTYPE_REVIEW.md](PROTOTYPE_REVIEW.md)): long polling → вебхук; in-memory → Postgres; модельная «система УК» и демо-таймер статусов → роль диспетчера УО в мини-приложении; UI-поля в домене → рендер в `bot/`.

### D-004. Продуктовая концепция прототипа «chat-first AI-помощник» переработана (22.09, Claude, ждёт подтверждения команды)
Прототип исходил из идеи «житель описывает проблему словами, AI задаёт вопросы и пишет текст обращения». Оставляем личный диалог как точку входа (арендатор, QR, проверяющий), но ядром продукта делаем заявку с нормативным сроком, коллективность в домовом чате и диспетчерскую УО ([PRODUCT.md](PRODUCT.md)). Почему: организаторы предупреждают не начинать с «AI-ассистента»; критерии дают 35 % за масштабирование и ничего за собственную модель; текст обращения жителю не нужен, если заявка сама регистрируется. Альтернатива: оставить концепцию прототипа — проще, но не отличается от десятков команд.

### D-005. ML-классификация жалоб: категория и аварийность через CatBoost, LLM для фото и уточнений; `ml/` (LoRA) удалён (22.09, ML-инженер команды)
**Решение:** два сценария конвейера классификации жалобы.
1. Текст жалобы → классификатор **CatBoost** определяет (а) категорию/подкатегорию (замена `guess_category()` по ключевым словам в [`catalog.py`](../backend/src/domain/tickets/catalog.py)) и (б) **аварийность** (`is_emergency`) — оба выхода идут напрямую в `SlaPolicy(category, is_emergency, ...)` и определяют легальный срок ([DATA.md §2](DATA.md)). Это не сортировка очереди «для удобства» — это тот же механизм, что в справочнике даёт лифту «≤1 сутки» или «≤30 мин», если внутри текста есть признак аварии (топит, искрит, заблокирован человек), а не просто «неисправность». Категория без аварийности не даёт правильный срок и наоборот — нужны оба выхода. Дальше очередь диспетчера сортируется по остатку времени до `resolve_by` (`sort=sla` в [CONTRACTS.md](CONTRACTS.md)) — это уже бесплатно после корректной классификации, отдельная модель «приоритета для сортировки» не нужна. Если к жалобе приложено фото, хостинговая **LLM через API** (провайдер по Q-09) по фото и тексту генерирует более подробное описание, которое прикрепляется к заявке для диспетчера — исходный текст жителя не заменяется.
2. Если уверенность классификатора (по категории или по аварийности) ниже порога, вместо мгновенной регистрации подключается **LLM-чат**: задаёт уточняющие вопросы и/или просит фото (если не приложено), по итогам формирует финальный текст — им заменяется исходное сообщение жителя. Это редкий fallback-путь, не основной сценарий (см. «Почему»). Правило fail-safe: при низкой уверенности именно в аварийности заявка по умолчанию считается аварийной (быстрый срок), пока fallback-диалог не уточнит обратное — недооценённая авария опаснее, чем лишняя быстрая реакция.

Прежний каркас дообучения LoRA в `ml/` (датасет, обучение, оценка, `TRAINING_PLAN.md`) удалён целиком — не потребуется.

**Почему:** CatBoost не требует GPU и обучается за минуты на CPU-датасете — реалистично для 8 дней, в отличие от прежнего плана дообучения LoRA. Аварийность — не отдельная «модель приоритета для сортировки», а обязательный вход SLA-расчёта (правка после обсуждения с ML-инженером: справочник в DATA.md §2 явно показывает, что один и тот же тип проблемы даёт разный срок в зависимости от признаков аварии в тексте, не только от категории/кнопки). Хостинговая LLM только для двух точечных случаев (фото, низкая уверенность) — то, что уже разрешено организаторами и рекомендовано в Q-09, без риска держать свой inference-эндпоинт две недели проверки. Fallback-чат — именно fallback, а не входная точка сценария, поэтому не противоречит предупреждению организаторов не начинать с «AI-ассистента» (D-004).

**Альтернативы:** (а) дообучение LoRA — отклонено, см. [PROTOTYPE_REVIEW §4](PROTOTYPE_REVIEW.md#4-ml-часть-дообучение-lora) (GPU, датасет на 4000 примеров, критерии не награждают свою модель); (б) классификация только кнопками/словарём (исходный P0 из Q-09) — отклонено, не различает аварию и обычную заявку внутри одной категории, только CatBoost на тексте это тянет; (в) отдельная модель приоритета поверх готовой SLA-сортировки — отклонено как избыточное: очередь и так сортируется по времени до дедлайна, как только `is_emergency` определена верно; (г) LLM-классификатор вместо CatBoost — отклонено, дороже по латентности и стоимости на каждую заявку там, где хватает лёгкой модели.

**Открыто (см. также Q-09):** размеченный корпус текстов жалоб для обучения CatBoost, с разметкой не только категории, но и аварийности по формулировке — в [DATA.md §4](DATA.md) есть только распределение по категориям, датасет предстоит собрать/сгенерировать; выбор конкретного vision-провайдера (поддержка изображений у GigaChat/YandexGPT не проверена); порог уверенности для fallback-чата, отдельно для категории и для аварийности.

### D-006. Классификатор — отдельный HTTP-сервис `ml/`, не код в процессе бота (22.09, ML-инженер команды)
**Решение:** CatBoost из D-005 живёт не внутри `backend/`, а отдельным сервисом `ml/` (свой `pyproject.toml`, свой Docker-контейнер, свой процесс FastAPI/uvicorn на порту 8100). Контракт — `POST /classify {text} -> {category_code, category_confidence, is_emergency, emergency_confidence}`, плюс `GET /health`/`GET /ready` (подробно — [CONTRACTS.md](CONTRACTS.md)). Бэкенд обращается туда через `infrastructure/ml/http_classifier.py` (реализация порта `classifier.py` из D-005) и сам откатывается на `RuleBasedClassifier` (ключевые слова), если сервис недоступен, ответил не 200 или вернул 503 (модели ещё не загружены) — тот же паттерн отказоустойчивости, что уже используется для LLM (`infrastructure/llm/service.py` → `StubAIService`). Обученные модели (`.cbm`-файлы) кладутся в `ml/models/` (том в `compose.yaml`, в `.gitignore` — бинарники не коммитятся) и подхватываются без пересборки образа: перезапустить только сервис `ml`, бот трогать не нужно.

**Почему:** ML-инженер и его датасет-напарник могут разрабатывать, обучать и перезапускать классификатор независимо от Python-окружения бота — не тащить `catboost`/`pandas`/`numpy` (и то, что дальше появится для экспериментов) в тот же venv/образ, что MAX-бот, не ждать друг друга по ревью и деплою. Порт `Classifier` (D-005) для этого и существовал — переключение с in-process адаптера на HTTP не потребовало менять use case'ы или домен, только один адаптер и конфиг.

**Альтернативы:** (а) CatBoost в процессе бота (`infrastructure/ml/catboost_classifier.py`, был реализован и удалён этим решением) — самый простой вариант, CatBoost лёгкий и не требует GPU/vLLM (в отличие от LoRA), но привязывает разработку модели к Python-окружению и релизному циклу бэкенда; отклонено по явному запросу ML-инженера. (б) Не заводить отдельный сервис, обучать модель и коммитить только `.cbm`-файл в `backend/` — не даёт независимости в разработке, тот же venv. Обе альтернативы дешевле по инфраструктуре (на один контейнер меньше) — см. риск ниже.

**Компромисс, который стоит держать в голове:** четвёртый контейнер на двухнедельный период проверки (30.09–14.10) — ещё одна точка отказа сверх уже учтённых в [STATUS.md](STATUS.md) рисков хостинга. Смягчено тем, что откат на правила уже встроен: падение `ml/` не роняет бота, только откатывает классификацию на ключевые слова до перезапуска. `docker compose` и `restart: unless-stopped` для сервиса `ml` — обязательны, как и для `bot`.

## Открытые вопросы (нужно решить команде 22–23.09)

### Q-01. Продуктовый фокус
**Рекомендация:** «заявка из домового чата с нормативным сроком + диспетчерская УО + эскалация» ([PRODUCT.md](PRODUCT.md)).
Почему: прямо названо экспертом трека (подтверждение, агрегация 50 чатов, арендатор), есть правовой драйвер, свободная ниша по ресерчу (MARKET §7), даёт двустороннюю демонстрацию и место для сильного фронта.
Альтернативы: (а) жилищный навигатор по капремонту — данные закрыты, придётся всё моделировать, слабая демонстрация; (б) сбор позиций/ОСС — пересекается с Госуслуги.Дом, юридически сложнее; (в) «умный» помощник по ЖКХ на LLM — то, что сделают все, и организаторы предупредили против «AI-ассистента».

### Q-02. Приоритетный пользователь в демо
**Рекомендация:** житель домового чата (включая арендатора) — первичный; диспетчер УО — второй экран демо. Председатель совета МКД — упоминание.
Почему: критерий «пользовательская ценность» требует одного конкретного сегмента; двусторонность показывает целостность продукта.

### Q-03. Формат: бот + мини-приложение или только бот
**Рекомендация:** бот + мини-приложение.
Почему: бонус +0,15 за осмысленную связку; очередь диспетчера, таймлайн и фильтры — ровно случаи для мини-приложения по PDF 15; это наш сильный фронт. Риск: URL мини-приложения прописывают организаторы, модерация до 48 рабочих часов → отправить форму не позже 25–26.09. Альтернатива: только бот — безопаснее по срокам, но теряем бонус и дифференциацию.

### Q-04. Точка входа: групповой чат или личный диалог
**Рекомендация:** групповой чат как основа, личный диалог + QR/диплинк дома как обязательный запасной путь (он же — сценарий арендатора и путь проверяющего). Личный диалог уже реализован в прототипе (D-003).
Почему: сила идеи — «чат → действие». Риск: у бота организаторов может быть запрещено добавление в группы; проверить 22.09 и сразу написать организаторам. Если запрет останется, демо делаем в диалоге, а групповой режим показываем на своём отладочном боте (если у кого-то есть статус самозанятого) или описываем как ограничение.

### Q-05. Backend-стек
**Рекомендация:** Python 3.13, FastAPI, SQLAlchemy 2 async + Alembic, PostgreSQL 17, `uv`, без Redis в P0 (очередь и лимитер в Postgres), фоновые воркеры в том же процессе. Архитектура — [ARCHITECTURE.md](ARCHITECTURE.md).
Почему: команда сильна в этом, шаблон переиспользуется; эксперты штрафуют сложность ради сложности. Альтернативы: Go/TS (официальные SDK MAX) — потеря скорости команды; Redis/Celery — лишние компоненты для MVP.

### Q-06. Клиент MAX API: свой адаптер или `maxapi`
**Рекомендация (пересмотрена 22.09 после прототипа):** оставить `maxapi` 1.2.2 как транспорт (разбор `Update`, `Dispatcher`/`Router`/фильтры, `FastAPIMaxWebhook`), но исходящие вызовы завернуть в порт `MaxGateway` (лимит 2/с на чат, retry, outbox), а состояние диалога хранить в Postgres вместо `MemoryContext`.
Почему: прототип на `maxapi` уже работает и проверен симулятором; переписывать транспорт ради чистоты — потеря 1–2 дней; порт `MaxGateway` даёт контроль там, где он нужен (лимиты, идемпотентность), а типы `maxapi` не проникают в домен. Альтернатива: свой httpx-клиент по OpenAPI — чище, но дороже; остаётся запасным, если `maxapi` подведёт на вебхуках (проверить 23.09).

### Q-07. Frontend-стек мини-приложения
**Рекомендация:** Vite + React + TypeScript + Tailwind 4; компоненты MAX UI (`@maxhub/max-ui`) для нативного вида, если заведётся с нашей версией React (заявлен React 18+); иначе shadcn из шаблона со стилизацией под MAX. Проверить 22–23.09 за 1–2 часа.
Почему: организаторы рекомендуют React и MAX UI; нативный вид в MAX — плюс к UX (20%). Альтернатива: свой дизайн на shadcn — быстрее, но выглядит «сайтом внутри мессенджера».

### Q-08. Хостинг и домен
**Рекомендация:** VPS в РФ (Timeweb Cloud или Selectel), домен второго уровня, Caddy с Let's Encrypt, `docker compose` на сервере, автозапуск; watchdog-cron на период проверки 30.09–14.10. Решить сегодня: чей аккаунт и карта, кто админит.
Почему: вебхуку нужен HTTPS 443 с доверенным сертификатом; бот должен быть онлайн две недели без вмешательства. Альтернатива: VK Cloud (бонус 2500 ₽/мес на хостинг мини-приложений) — стоит попробовать параллельно, но не как единственный вариант.

### Q-09. LLM в продукте (сужено после D-005)
**Рекомендация:** классификация категории — CatBoost, не LLM (см. [D-005](#d-005-ml-классификация-жалоб-категория-и-аварийность-через-catboost-llm-для-фото-и-уточнений-ml-lora-удалён-2209-ml-инженер-команды)), поэтому это не «AI-ассистент с порога». LLM через API остаётся для двух точечных случаев из D-005 — описание по фото и уточняющий диалог при низкой уверенности классификатора, оба P1, не основной путь. Провайдер — российский (GigaChat/YandexGPT, точный выбор открыт — нужна поддержка изображений), ключ только в `.env`, ответы с указанием источника нормы там, где применимо.
Почему: организаторы прямо предупреждают не начинать с «AI-ассистента» и требуют привязки к источникам; демонстрация не должна зависеть от внешнего сервиса дольше, чем нужно для двух точечных задач.
