# Интеграция с CRM, 1С и АДС управляющей организации

Руководство для разработчика на стороне УО и для того, кто решает, как подключить «Домового» к рабочей системе диспетчеров. Реализовано 30.09.2026 ([D-016](DECISIONS.md)). Живая спецификация: `https://domovoy.prooood.ru/integration/v1/docs` (Swagger), `…/integration/v1/openapi.json` (OpenAPI 3.1, вместе с описанием исходящего вебхука).

## 1. Что это даёт

Житель по-прежнему пишет в MAX, а диспетчер УО работает в своей CRM, 1С или АДС. Заявка из MAX сама появляется в системе УО с нормативным сроком и правовым основанием. Статус, который диспетчер ставит у себя, сразу уходит жителю в MAX. Ответ жителя («Починили» / «Не починили») возвращается в систему УО. У заявки два номера — «Домового» и системы УО, — и они связаны.

Двойного ввода и второй очереди нет, диспетчер не открывает ещё один кабинет.

## 2. Почему без адаптера под каждую CRM

CRM у УО разные, и заранее неизвестно, какая будет у конкретной компании. Поэтому «Домовой» не подстраивается под каждую систему, а даёт **один контракт**, который реализуется на любой системе, умеющей HTTP и JSON:

| Направление | Как | Когда подходит |
|---|---|---|
| «Домовой» → система | **Вебхук**: POST с событием на ваш HTTPS-адрес, подпись HMAC-SHA256 | система принимает входящие запросы: облачная CRM, свой сервис, no-code платформа |
| «Домовой» → система | **Лента событий**: `GET /events?after=<курсор>` — те же события, забираете сами | входящие запросы невозможны: 1С в локальной сети, за NAT, обмен по расписанию |
| система → «Домовой» | **REST**: сменить статус, привязать свой номер, выгрузить заявки, посчитать нормативный срок | всегда |

Особенности конкретной системы сводятся к **данным, а не к коду**:

- **таблица статусов** (`PUT /status-map`): ваши коды `WORKING` или `В работе` → наш `in_progress`. После этого вы шлёте и получаете свои коды как есть;
- **ваш номер заявки**: верните его в ответе на вебхук или передайте через `PUT /tickets/{ref}/external`. Дальше обращайтесь к заявке по нему: `/tickets/ext:58391`;
- **набор событий**: подписка только на нужные типы.

Если у системы нет программиста, но есть no-code коннектор (например n8n, Make, Albato), который умеет «принять вебхук» и «выполнить HTTP-запрос», связка собирается без кода. Готовых модулей под конкретные платформы мы не делали: это обычные HTTP-вызовы.

## 3. Подключение по шагам

Ниже `$API=https://domovoy.prooood.ru/integration/v1` и `$KEY` — ключ.

**1. Получить ключ.** Ключ выдаёт диспетчер УО, и он действует только для заявок своей УО. Сейчас это делается одним из двух способов:

- REST мини-приложения: `POST /api/v1/dispatcher/integrations {"name": "1С:Жилищный стандарт"}` с авторизацией `tma <initData>` диспетчера. В ответе `api_key` (показывается один раз), `api_base_url` и `docs_url`.
- Скрипт оператора: `DATABASE_URL=… PYTHONPATH=src uv run python -m scripts.integration_key --dispatcher <max_user_id> --name "CRM"`.

Кнопки в интерфейсе мини-приложения пока нет (§9). Отозвать ключ: `DELETE /api/v1/dispatcher/integrations/{id}` — он перестаёт работать сразу.

**2. Проверить ключ.**
```bash
curl -H "Authorization: Bearer $KEY" $API/me
```
Вместо `Authorization` можно передать ключ в заголовке `X-Api-Key: $KEY`: так бывает удобнее в no-code инструментах.

**3. Задать свои статусы** (необязательно):
```bash
curl -X PUT -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" $API/status-map \
  -d '{"map": {"NEW":"registered","ACCEPTED":"acknowledged","WORKING":"in_progress","DONE":"done","CANCELLED":"rejected"}}'
```
Наши коды и их смысл — `GET /reference`.

**4. Подключить вебхук** — если ваша система принимает входящие запросы:
```bash
curl -X PUT -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" $API/webhook \
  -d '{"url": "https://crm.example.ru/hooks/domovoy"}'
# → {"url": "...", "event_types": [...], "secret": "whsec_..."}
```
Сохраните `secret`: им проверяется подпись. `rotate_secret: true` выпускает новый секрет, `url: null` выключает вебхук. Вебхук начинает со следующего изменения; историю можно забрать из ленты (`GET /events?after=0`) или списком (`GET /tickets`).

**5. Проверить доставку:** `POST /webhook/test` сразу отправляет подписанный `ping` и показывает, что ответил ваш сервер.

**6. Принимать события** (§4) и **менять статусы** (§5).

## 4. События: «Домовой» → ваша система

| Тип | Когда |
|---|---|
| `ticket.created` | житель подал заявку: в личке, в мини-приложении или из домового чата |
| `ticket.status_changed` | любой переход: диспетчер, ваша система, житель подтвердил или переоткрыл. `data`: `previous_status`, `status`, `actor` (`resident` / `dispatcher` / `integration`), `comment` |
| `ticket.supported` | сосед нажал «У меня тоже»; `data.supporters_count` |
| `ticket.overdue` | нормативный срок прошёл, а заявка открыта |
| `ticket.escalated` | житель запросил жалобу в жилинспекцию |

Тело одинаковое у вебхука и у ленты:

```json
{
  "id": "5b0c…",            "seq": 128,
  "type": "ticket.created", "schema_version": 1,
  "occurred_at": "2026-09-30T09:00:00+00:00",
  "integration_id": "…",
  "ticket": {
    "id": "018f…", "number": "2026-01042", "status": "registered",
    "category": {"code": "lift", "title": "Лифт"}, "is_emergency": false,
    "description": "Лифт не работает", "building": {"id": "…", "address": "г. Псков, ул. …"},
    "responsible_party": "management_company", "responsibility_basis": "…",
    "deadlines": {"react_by": null, "resolve_by": "2026-10-01T12:00:00+03:00",
                  "legal_basis": "Правила № 170, прил. 2: неисправность лифта — до 1 суток"},
    "is_overdue": false, "source": "max_bot", "supporters_count": 0, "photo_urls": [],
    "escalated_at": null, "created_at": "…", "updated_at": "…",
    "timeline": [{"status": "registered", "actor": "resident", "at": "…", "comment": null}],
    "external": null, "crm_status": "NEW"
  },
  "data": {}
}
```

`ticket` — заявка на момент события. `external` — ваша запись, если заявка уже связана. `crm_status` — статус в ваших кодах.

**Заголовки вебхука:** `X-Domovoy-Event-Id`, `X-Domovoy-Event-Type`, `X-Domovoy-Timestamp` (unix-время), `X-Domovoy-Signature: sha256=<hex>`. Подпись — HMAC-SHA256 секретом вебхука от строки `<timestamp>.<сырое тело запроса>`. Отклоняйте запросы старше 5 минут: так повтор перехваченного запроса не пройдёт.

```python
import hashlib, hmac, time

def is_valid(secret: str, timestamp: str, body: bytes, signature: str) -> bool:
    if abs(time.time() - int(timestamp)) > 300:
        return False
    digest = hmac.new(secret.encode(), timestamp.encode() + b"." + body, hashlib.sha256)
    return hmac.compare_digest("sha256=" + digest.hexdigest(), signature)
```

```js
// Node.js: body — сырое тело (Buffer), до JSON.parse
const crypto = require("crypto");
const expected = "sha256=" + crypto.createHmac("sha256", secret)
  .update(`${timestamp}.`).update(body).digest("hex");
const ok = Math.abs(Date.now() / 1000 - Number(timestamp)) <= 300 &&
  expected.length === signature.length &&
  crypto.timingSafeEqual(Buffer.from(expected), Buffer.from(signature));
```

```php
// PHP: $body = file_get_contents('php://input');
$expected = 'sha256=' . hash_hmac('sha256', $timestamp . '.' . $body, $secret);
$ok = abs(time() - (int)$timestamp) <= 300 && hash_equals($expected, $signature);
```

**Ответ.** Ответьте `2xx` не дольше чем за 10 секунд. На `ticket.created` можно сразу вернуть свою запись, и заявка свяжется без второго запроса:

```json
{"external_id": "58391", "external_number": "АДС-58391", "external_url": null}
```

**Доставка.**

- Каждое событие доставляется хотя бы один раз и по порядку. Повторы отбрасывайте по `id`.
- При `5xx`, `408`, `409`, `425`, `429`, `3xx` (редиректы не выполняем), таймауте или сетевой ошибке доставка повторяется с паузами 10 с → 1 мин → 5 мин → 30 мин и дальше раз в 30 минут. Пока вы недоступны, события ждут, ни одно не теряется.
- Остальные `4xx` означают «событие не принимаем»: мы его пропускаем, чтобы одно событие не блокировало очередь. Из ленты его можно забрать в любой момент.
- Ваши собственные изменения (статус, поставленный через API этим ключом) эхом не возвращаются.
- Задержка — несколько секунд. Состояние доставки видно в `GET /me` → `webhook`: `pending_events`, `last_success_at`, `last_error`, `next_attempt_at`.

**Лента вместо вебхука** — для систем, к которым нельзя достучаться снаружи. Храните у себя курсор `after` и опрашивайте, например, раз в минуту:

```bash
curl -H "Authorization: Bearer $KEY" "$API/events?after=0&limit=100"
# → {"events": [...], "next_after": 128, "has_more": false}
```

Набросок для 1С (проверьте в своей конфигурации):


## 5. Ваша система → «Домовой»

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/me` | подключение, таблица статусов, состояние вебхука |
| PUT | `/webhook` | адрес, типы событий, секрет |
| POST | `/webhook/test` | тестовый `ping` прямо сейчас |
| PUT | `/status-map` | ваши коды → наши |
| GET | `/events?after=&limit=` | лента событий по курсору |
| GET | `/tickets?cursor=&limit=` | все заявки УО по времени изменения: первичная загрузка и сверка |
| GET | `/tickets/{ref}` | карточка заявки |
| PUT | `/tickets/{ref}/external` | связать с вашей записью: `{id, number?, url?, status?}` |
| POST | `/tickets/{ref}/status` | сменить статус: `{status, comment?, external?}`; житель получит уведомление в MAX |
| POST | `/sla/calculate` | нормативный срок и основание для заявки из вашей системы: `{category_code, is_emergency, registered_at?}` |
| GET | `/reference` | коды категорий, статусов, событий |

`{ref}` — наш id (UUID), наш номер (`2026-01042`) или ваш id после связывания (`ext:58391`).

**Правила статусов.** Система действует от имени УО, по тем же правилам, что и диспетчер: `acknowledged`, `in_progress`, `done`, `rejected`. Подтвердить устранение (`confirmed`) и переоткрыть заявку после `done` может только житель: так результат подтверждает тот, у кого была проблема. Недопустимый переход — `409 illegal_transition`, недопустимый для УО статус — `403 action_not_allowed`. Повтор того же статуса ничего не меняет и возвращает `applied: false`, поэтому повторять запросы безопасно. Неизвестный код — `422 unknown_status`: мы не угадываем статус, который увидит житель.

**Нормативный срок как сервис.** `POST /sla/calculate` считает срок реакции и устранения по категории и аварийности, с календарём рабочих дней и ссылкой на норму, и заявку при этом не создаёт. Так УО может получить главное отличие «Домового» — проверяемый нормативный срок — даже для заявок, которые пришли не из MAX. Время без часового пояса читается как московское. Поле `needs_verification` показывает, что норма взята из вторичного источника и ждёт юридической сверки ([DATA.md §2](DATA.md)).

**Ошибки** — `application/problem+json` с `error_code`:

| Код | `error_code` |
|---|---|
| 401 | `invalid_api_key` |
| 403 | `action_not_allowed` |
| 404 | `ticket_not_found` |
| 409 | `illegal_transition`, `external_id_taken` |
| 422 | `unknown_status`, `webhook_url_rejected` |
| 400 | `invalid_cursor` |

## 6. Сквозной пример: mock CRM

`backend/scripts/mock_crm.py` — маленькая «CRM управляющей организации» на тестовых данных. Она:

- при старте регистрирует свою таблицу статусов и вебхук;
- проверяет подпись входящих событий;
- присваивает заявке свой номер «АДС-…» и возвращает его в ответе;
- показывает страницу `http://localhost:8200` с кнопками «Принять», «В работу», «Выполнено».

```bash
# бэкенд локально; вебхук на http://localhost разрешается только так:
INTEGRATIONS_ALLOW_PRIVATE_URLS=true DEV_AUTH_ENABLED=true … (запуск бэкенда, backend/README.md)
curl -X POST localhost:8080/api/v1/dispatcher/integrations -H "Authorization: dev <id диспетчера>" \
  -H "Content-Type: application/json" -d '{"name":"Mock CRM"}'          # → api_key
cd backend && DOMOVOY_API_KEY=dmv_… PYTHONPATH=src uv run python -m scripts.mock_crm
```

Сценарий, проверенный 30.09 на двух процессах и PostgreSQL:

1. Житель подаёт заявку.
2. Через пару секунд она появляется в mock CRM с номером АДС, а в «Домовом» становится видна по `ext:<номер>`.
3. Диспетчер в mock CRM нажимает «В работу», затем «Выполнено». Жителю уходят уведомления с комментариями, а mock CRM не получает свои же изменения обратно.
4. Житель отвечает «Не починили» — mock CRM получает `ticket.status_changed` с `actor: resident`.
5. Повтор статуса возвращает `applied: false`.
6. Mock CRM выключена, житель подаёт заявку: событие ждёт в очереди, а в `GET /me` видны `last_error` и время следующей попытки. После включения CRM событие доставляется, ошибка сбрасывается.

На стенде вебхук должен быть публичным HTTPS-адресом. Для проверки подойдёт любой публичный приёмник запросов или no-code платформа. Лента `GET /events` работает без вебхука.

## 7. Безопасность и персональные данные

- Наружу уходят только данные для исполнения заявки: текст, адрес дома, категория, срок, фото, таймлайн. Идентификаторов пользователей MAX, имён и телефонов в событиях нет (проверяется тестом).
- Ключ хранится только как SHA-256-хэш и показывается один раз. Каждый ключ видит только заявки своей УО: чужая заявка для него «не найдена».
- Вебхук принимается только на `https://`. Внутренние адреса (localhost, частные сети, link-local, метаданные облака) запрещены, в том числе после DNS-резолва, а редиректы не выполняются: адрес задаёт внешняя сторона, и он не должен вести во внутреннюю сеть (SSRF). Для локальной разработки есть `INTEGRATIONS_ALLOW_PRIVATE_URLS=true`, в проде его не включать.
- Подпись с меткой времени защищает от подмены и от повтора перехваченного запроса.

## 8. Как устроено внутри

Любое изменение заявки записывает событие в таблицу `integration_events` **в той же транзакции**, что и само изменение (transactional outbox, как у уведомлений). Поэтому событие не теряется и не расходится с заявкой, а недоступность CRM не мешает жителю. Позиция события в ленте — `seq`, её же использует курсор вебхука каждого подключения (`integrations.delivered_seq`). Фоновая задача раз в пару секунд доставляет события по порядку. Связи номеров хранятся в `external_ticket_links`. Модель данных — [DATA.md](DATA.md), решение — [D-016](DECISIONS.md), код:

| Слой | Где |
|---|---|
| домен | `backend/src/domain/integrations/` (подключение, событие, связь, таблица статусов) |
| use case'ы | `backend/src/application/integrations/` (по одному на файл) |
| БД | `backend/src/infrastructure/db/integration*.py`, миграция `0007_integrations.py` |
| HTTP и подпись | `backend/src/infrastructure/integrations/` |
| API | `backend/src/api/integration/` (`/integration/v1`), `backend/src/api/http/v1/integrations.py` (диспетчер) |
| тесты | `backend/tests/unit/application/test_integrations.py`, `tests/unit/app/test_integration_api.py`, `tests/unit/test_webhook_security.py`, `tests/integration/test_sql_integrations.py` |

## 9. Чего пока нет

- **Кнопки «Подключить CRM» в мини-приложении.** API для неё готов (`/api/v1/dispatcher/integrations`), экрана нет.
- **Комментария без смены статуса.** Сейчас комментарий передаётся вместе со статусом.
- **Файлового обмена** (CSV/JSON для систем без API) и конструктора соответствий: в [INTEGRATION_IDEAS.md](INTEGRATION_IDEAS.md) это I-09 и K-06.
- **Лимитов частоты запросов**, журнала отдельных попыток доставки и ручного replay: сейчас видна только последняя ошибка, а replay делается через ленту.
- **Ротации ключа одной операцией**: сейчас нужно выдать новый ключ и отозвать старый.
- **Фильтра по домам** внутри одной УО: подключение видит все её дома.
- **Проверки с реальной CRM.** Подключение проверено на mock CRM. Для заявления «интегрировано с X» нужны тестовый контур и согласие владельца системы.
