# Ревью прототипа бота (коммиты на `main` от 22.09)

Автор прототипа: участник команды, 17 коммитов, ~3 000 строк Python (бот ~1 900, ML ~1 300). Ревью и переезд по слоям сделал Claude 22.09 по просьбе Марка. Всё, что ниже, — предложение; спорные пункты вынесены в [DECISIONS.md](DECISIONS.md) (D-003, D-004, Q-06, Q-17).

## 1. Что сделано в прототипе

Личный диалог с ботом на `maxapi` 1.2.2: `/start` → меню → быстрые категории или свободный текст → «AI» задаёт один уточняющий вопрос → черновик текста обращения (правится сообщением) → «Готово» → отправка в модельную систему УК (HTTP POST или mock) → номер и статус → «Мои обращения». Статусы двигает демо-таймер, уведомления приходят в чат. Плюс каркас дообучения LoRA (Qwen2.5-7B) для вопросов и генерации текста, не запускался.

## 2. Что хорошо и остаётся

- **Навигация «одним сообщением»** (`bot/screen.py`): экран перерисовывается через `POST /answers` и `PUT /messages`, при сбое отправляется новое сообщение. Это наш примитив и для карточки заявки в домовом чате.
- **Чистый, читаемый код**: докстринги, маленькие модули, разделены тексты, клавиатуры, payload'ы, справочник категорий, обработчик ошибок без тупиков, идемпотентная повторная отправка (дубликат заявки не создаётся).
- **Контракт AI-слоя как порт** (`AIService` с `analyze`/`refine`) и заглушка на правилах: LLM подключается без правок хендлеров. Строгая JSON-схема ответа модели с валидацией и откатом на заглушку — правильный подход, совпадает с требованием кейса «не выдавать предположение модели за факт».
- **Оффлайн-симулятор** с фейковым транспортом: четыре сценария, проверка, что чат не засоряется. После переезда проходит целиком.
- README прототипа сделан по чек-листу кейса, Dockerfile с непривилегированным пользователем.

## 3. Что расходится с требованиями и нашим видением

| Расхождение | Почему важно | Что делаем |
|---|---|---|
| **Long polling** в проде | MAX на Q&A: «используйте вебхуки», polling только для разработки; бот должен жить 2 недели проверки | Вебхук через `maxapi` + FastAPI за Caddy (443, Let's Encrypt), переподписка при старте |
| **In-memory** хранилище и FSM (`MemoryContext`) | Заявки и состояние диалога теряются при перезапуске; проверяющие увидят «данные сброшены» | PostgreSQL: репозитории, `DialogState` в БД, inbox/outbox |
| **Продукт = AI-помощник, который пишет текст обращения** для одного жителя | Организаторы прямо предупреждают: не начинать с «AI-ассистента»; это сделают многие команды; нет нормативного срока, нет коллективности, нет стороны УО | Ядро — заявка со сроком по нормативу и статусами; текст обращения второстепенен. Личный диалог остаётся как точка входа (арендатор, QR) |
| **УК как внешняя система** (`UKClient`, HTTP POST, случайные статусы по таймеру) | Реального API УК нет и не будет; таймер статусов — имитация интеграции, которую кейс запрещает выдавать за реальную | УО — **пользователь нашего продукта**: роль диспетчера в мини-приложении меняет статусы руками. `UKClient` и демо-таймер убираем |
| **Домен знает про UI** (`RequestStatus.emoji`, `label`, `short_title`), статус меняется без проверки переходов | Критерий «архитектура»: логика должна быть отделена и развиваема | Явная таблица переходов в `domain/tickets/state_machine.py`, эмодзи и подписи — в `bot/render` |
| Глобальный синглтон `get_services()` в хендлерах | Тестируемость, скрытые зависимости | DI через middleware диспетчера или контейнер в `app/` |
| Payload кнопок «ограничен 256 символами» | По схеме API — 1024 (наши соглашения в CONTRACTS §2) | Поправить комментарий, использовать `ns:action:arg` |
| `MAX_BOT_TOKEN`, «выдаёт @MasterBot» | У нас `MAX_TOKEN`; токен выдали организаторы, `@MasterBot` — из другого мессенджера | Исправлено: конфиг читает `MAX_TOKEN` (fallback `MAX_BOT_TOKEN`), тексты поправлены |
| Дублирующие контекстные документы `AGENT(2).md`, `PROGRESS.md` | Два источника истины расходятся | Уникальные решения перенесены в DECISIONS (D-003, D-004), файлы удалены; точка входа — `AGENTS.md` |
| Файлы в корне (`app/`, `ml/`, `scripts/`, Dockerfile, requirements) | Наш макет — `backend/`, `frontend/`, `infra/`, `docs/` | Перенесено, см. §5 |

## 4. ML-часть: дообучение LoRA

> Обновлено 22.09 вечером: рекомендация ниже (заморозить и не дообучать) принята и расширена — см. [DECISIONS.md D-005](DECISIONS.md#d-005-ml-классификация-жалоб-категория-и-аварийность-через-catboost-llm-для-фото-и-уточнений-ml-lora-удалён-2209-ml-инженер-команды). Каркас LoRA из `ml/` удалён; классификация — CatBoost, LLM через API только точечно (фото, fallback). Текст ниже — исходное обоснование решения, оставлено как контекст.

Каркас грамотный (контракт, промпты общие для обучения и инференса, метрика выдуманных норм, откат на заглушку). Но как задача хакатона это **не окупается**:

- Ни строка не запускалась; нужен GPU 24 ГБ, ~4 000 примеров (из них 300–600 вручную), vLLM-эндпоинт, который должен жить с 30.09 по 14.10 (стоимость GPU-хостинга на две недели). План обучения занимает все 8 дней одного человека.
- Задача модели — задавать уточняющие вопросы и писать текст обращения. Обе вещи закрываются кнопками и шаблонами без потери ценности для жителя; критерии не дают баллов за собственную модель, а «сложность ради сложности» штрафуют.
- Если LLM всё же нужна для свободного текста, дешевле вызвать хостинговую российскую модель (GigaChat / YandexGPT, OpenAI-совместимый API) через уже написанный `infrastructure/llm/client.py` — организаторы это прямо разрешили.

**Рекомендация (Q-17):** `ml/` заморозить как исследовательский пакет вне P0–P2 онлайн-этапа; вернуться к нему только после выхода в финал, если останется время. Автору — переключиться на диспетчерскую УО или групповой чат: это критерии на 35 % + 20 %.
