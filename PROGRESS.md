## 2026-09-22 — Первая рабочая версия MAX-бота

### Запрос
Реализовать чат-бота в MAX на библиотеке `maxapi` по CJM: приветствие
с меню → создание обращения (быстрые сценарии + свободный текст) →
AI-уточнения и генерация текста обращения → «Готово» → отправка в УК →
«Мои обращения» со статусами. Главное требование к UX: навигация
должна перерисовывать текущее сообщение, а не слать новые.

### Сделано
- Каркас приложения: `app/` (config, services, states, callbacks,
  keyboards, texts, models, storage, notifier, screen).
- Навигация «одним сообщением» (`app/screen.py`): callback —
  редактирование через `send_callback`, текстовое сообщение —
  `edit_message` по сохранённому в FSM `screen_message_id`,
  с откатом на отправку нового сообщения при сбое.
- Сценарий создания обращения (`app/handlers/create.py`): быстрые
  категории, уточняющие вопросы, черновик, правка текстом, отправка.
- Раздел «Мои обращения» (`app/handlers/my_requests.py`): список
  кнопок в столбик + карточка со статусом, текстом и историей.
- Chat-first вход (`app/handlers/fallback.py`): свободный текст вне
  сценария сразу запускает оформление обращения.
- AI-заглушка `StubAIService` с контрактом `AIService`
  (`analyze` / `refine`) — подключение LLM без правок хендлеров.
- Модельная интеграция с УК `UKClient` с готовым боевым путём
  (HTTP POST по `UK_API_URL`) и обработкой таймаутов/ошибок.
- Демо-имитация смены статусов + уведомления в чат.
- Оффлайн-симулятор сценария `scripts/simulate_flow.py`.
- Комплектность сдачи: `requirements.txt`, `.env.example`,
  `Dockerfile`, `compose.yaml`, `.dockerignore`, README.

### Изменённые файлы
- `app/**`, `scripts/simulate_flow.py`
- `requirements.txt`, `.env.example`
- `Dockerfile`, `compose.yaml`, `.dockerignore`
- `README.md`, `PROGRESS.md`

### Технические решения
- Стек: Python 3.13 + `maxapi` 1.2.2, long polling (входящие порты
  не нужны, проще разворачивать).
- Состояние диалога — встроенный FSM `maxapi` (`MemoryContext`).
- Payload кнопок — короткие строки `действие:аргумент`; ID обращения
  передаётся числом, пользовательский текст в payload не попадает.
- Хранилище обращений — in-memory репозиторий с узким интерфейсом,
  чтобы заменить на БД без правок хендлеров.
- Роутер `fallback` подключается последним: диспетчер останавливается
  на первом сработавшем хендлере.
- Заявка создаётся один раз и переиспользуется при повторной отправке
  после сбоя УК — дубликатов нет.

### Проверка
- `python -m scripts.simulate_flow` — три сценария (быстрая кнопка,
  свободный текст, сбой УК) проходят полностью; отдельно подтверждено,
  что вся навигация выполняется в одном сообщении и новых сообщений
  в чат не отправляется.
- Сборка Docker-образа **не проверена**: на машине не запущен
  Docker daemon.
- В реальном мессенджере MAX бот не проверялся: нужен `MAX_BOT_TOKEN`.

### Известные проблемы / ограничения
- AI — заглушка на правилах, LLM ещё не подключена.
- Интеграция с УК модельная, статусы двигаются по демо-таймеру.
- Обращения не переживают перезапуск процесса.
- Фото и голос не обрабатываются.

### Следующий логичный шаг
- Прогнать бота с реальным токеном в MAX и снять первые замечания
  по UX (в частности, поведение `edit_message` в мобильном клиенте).
- Подключить LLM в `app/ai/service.py` вместо `StubAIService`.
- Решить вопрос персистентности (SQLite/Postgres) под демо на защите.

## 2026-09-22 — Основа собственной ML-модели (без обучения)

### Запрос
Реализовать основу модели, которая задаёт уточняющие вопросы по
ответам жителя и формирует текст обращения. Модель пока **не
обучать** — только каркас и всё, что нужно для обучения позже.

### Сделано
- `ml/schemas.py` — строгий JSON-контракт ответа модели
  (`ModelDecision`: `ask` / `draft`, слоты, срочность, объяснение)
  и определение обязательных слотов по категориям.
- `ml/prompts.py` — системный промпт и сборка чата; один и тот же
  модуль используется при обучении и на инференсе.
- `ml/dataset/` — формат обучающего примера (JSONL), генератор
  синтетических диалогов по шести категориям, CLI сборки train/val.
- `ml/training/` — конфиг (база, LoRA, гиперпараметры) и скрипт
  SFT-дообучения LoRA-адаптера; loss считается только на ответе
  модели.
- `ml/inference/` — HTTP-клиент OpenAI-совместимого endpoint'а и
  `LLMAIService`: валидация ответа, одна попытка починки, откат на
  `StubAIService`.
- `ml/evaluation/` — продуктовые метрики (валидность JSON, выбор
  действия, F1 по слотам, выдуманные нормативные ссылки) и скрипт
  приёмки на валидационной выборке.
- Подключение к боту: переменные `LLM_*`, выбор AI-слоя в
  `app/services.py`, закрытие клиента при остановке.
- Сценарий 4 в `scripts/simulate_flow.py`: бот поверх ответов модели.
- `requirements-ml.txt`, `ml/README.md`, обновлён основной README.

### Изменённые файлы
- `ml/**`, `requirements-ml.txt`
- `app/config.py`, `app/services.py`, `app/main.py`
- `scripts/simulate_flow.py`, `.env.example`, `.gitignore`
- `README.md`, `PROGRESS.md`

### Технические решения
- Модель отвечает **только структурированным JSON**: свободный текст
  в интерфейс не попадает, все экраны строит бот.
- Базовая модель — `Qwen/Qwen2.5-7B-Instruct`: Apache-2.0 (важно для
  правил хакатона), сильный русский, влезает в LoRA на 24 ГБ GPU.
- Дообучение — LoRA (PEFT/TRL) в 4-битном режиме; полный fine-tuning
  под сроки и железо не рассматривался.
- Модель обслуживается отдельно (vLLM), бот ходит по HTTP: в
  контейнере бота нет ни torch, ни весов, ML-зависимости вынесены
  в `requirements-ml.txt`.
- Надёжность важнее качества ответа: любой сбой модели откатывает
  сценарий на заглушку, житель не упирается в тупик.
- Метрика `invented_norms` введена намеренно: по требованиям брифа
  модель не должна выдавать домыслы о нормах за факт.

### Проверка
- `python -m ml.dataset.build --count 200` — выборка собирается,
  все целевые JSON проходят валидацию схемой.
- `python -m scripts.simulate_flow` — четыре сценария, включая
  работу бота поверх ответов модели, починку невалидного JSON и
  откат на заглушку при недоступности модели.
- **Модель не обучалась**: `ml/training/train_lora.py` и
  `ml/evaluation/run_eval.py` написаны, но ни разу не запускались —
  нужны GPU, ML-зависимости и поднятый endpoint.

### Известные проблемы / ограничения
- Весов модели нет, по умолчанию `LLM_ENABLED=false`.
- Обучающая выборка полностью синтетическая: шаблонный язык, нет
  опечаток, эмоций, нескольких проблем в одном сообщении.
- Длина диалога (число вопросов до обращения) пока не измеряется —
  нужен роллаут с имитацией ответов жителя.
- Скрипт дообучения не проверен на реальном железе: возможны правки
  под конкретные версии transformers/trl.

### Следующий логичный шаг
- Собрать 200–300 реальных/вручную проверенных диалогов и смешать
  с синтетикой.
- Прогнать первое дообучение, снять метрики, поднять endpoint.
- Добавить роллаут-оценку длины диалога.

## 2026-09-22 — План обучения модели

### Запрос
Подготовить план обучения модели (эпохи, гиперпараметры и всё
остальное, что нужно для эффективного обучения) отдельным
markdown-документом.

### Сделано
- `ml/TRAINING_PLAN.md`: требования к железу, целевой состав и
  правила разметки выборки, таблица гиперпараметров со связью с
  `ml/training/config.py`, расчёт шагов и времени, разбор по эпохам
  с признаками нормы и переобучения, критерии приёмки (go/no-go),
  замер baseline до дообучения, план по дням 22.09–29.09, правила
  воспроизводимости и таблица рисков.
- В `ml/training/config.py` добавлен `lr_scheduler_type="cosine"`
  и проброшен в `SFTConfig`; `save_total_limit` поднят до 5, чтобы
  выбирать лучший чекпоинт по метрикам, а не только по последним.
- Ссылки на план из `ml/README.md` и основного `README.md`.

### Изменённые файлы
- `ml/TRAINING_PLAN.md`, `ml/README.md`, `README.md`
- `ml/training/config.py`, `ml/training/train_lora.py`
- `PROGRESS.md`

### Технические решения
- Эффективный батч 16 (2 × 8): при выборке 4000 примеров это
  ~250 шагов на эпоху и ~750 шагов за 3 эпохи.
- Потолок — 3 эпохи: выборка на 85% синтетическая, дальше модель
  начинает дословно воспроизводить шаблоны.
- Лучший чекпоинт выбирается по метрикам `run_eval`, а не по
  eval loss: loss отражает формат, но не качество вопросов.
- Отдельный `val_real.jsonl` только из реальных диалогов — честная
  оценка качества на живом языке.
- Обязательный замер baseline базовой модели без адаптера: и
  контроль пайплайна, и цифра «было → стало» для защиты.

### Проверка
- Числа в плане пересчитаны из фактического конфига
  (`effective batch = 16`), длины примеров измерены на
  сгенерированной выборке: медиана ~1130 токенов, максимум ~1360
  при `max_seq_length=2048`.
- `python -m scripts.simulate_flow` — все четыре сценария проходят
  после правок конфига.
- Сам план на практике не проверялся: обучение не запускалось.

### Известные проблемы / ограничения
- Оценки времени обучения (1.5–6 ч) ориентировочные, их нужно
  пересчитать после замера скорости на реальной GPU в день 1.
- Скрипт дообучения по-прежнему не запускался на железе.

### Следующий логичный шаг
- День 1 плана: поднять окружение и прогнать smoke-run на 50 шагов.
